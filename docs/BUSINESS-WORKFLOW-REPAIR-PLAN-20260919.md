## 2. 本批已确认的业务决定

| 事项 | 建议采用的确定规则 |
| --- | --- |
| 应收口径 | Receivable 是应收唯一事实来源；FeeEntry 是登记和流水展示入口，不再另维护一套应收金额 |
| 款项分类 | 律师费、代收款、代垫回收及其他款项分开；只有明确属于律师费的到账进入律师费收入及自动分成 |
| 退款/冲正 | 提交后待确认，确认后生效；增加独立的财务更正确认权限 finance.correct（ALL），内置财务具备，其他账号由自定义角色明确配置 |
| 归档后业务 | 已批准卷宗保持不变；允许有权限者追加尾款、退款、核销、票据及必要收尾记录，不能借此编辑历史案情或新增代理范围 |
| 案件接管 | 增加专门权限 matters.transfer（ALL，默认不随超级管理员身份取得）；当前主办保留主动交接权，专门授权人员可应急接管 |
| 合同变更 | 明确追加、调减、替代总价、仅范围/期限变更、终止结算；草稿不参与有效合同额，旧合同保留 |
| 冲突复核 | 保存新事实可以继续；新增代理范围进入待复核，正式接受该范围前完成核查；不冻结原有案件的紧急事项和材料保存 |
| 开庭/期限责任 | 默认程序主办，缺省回退案件主办，可明确指派有效案件成员；责任变更需接收确认，未接收时原责任或应急负责人仍清晰可见 |

这些决定修订的是业务规则；不把普通界面显示当成授权，也不把超级管理员身份当成业务审批资格。

## 3. 修复一：统一财务事实与统计

### 3.1 收费到回款的唯一链条

1. 签署的收费安排产生分期应收计划。每期填写金额、到期日期或待成就条件；明确区分“未到期”“条件待成就”“未约定到期日”“已逾期”。
2. 条件型应收由人工确认条件已成就，并填写日期与依据后进入到期计算；不从付款节点自然语言中静默推算日期。
3. 收款登记仍一律先待确认；财务确认后生成一笔实收，重复提交/确认不能重复生成。
4. 在案件财务和全所财务增加“分配收款”入口：一笔款可分配到多期，一期可由多笔款结清；同一对收款/应收再次分配可正常累加并留痕。
5. 未分配款单独展示，不伪装成某一期已经结清。默认分配限定同一案件、相同资金性质；跨案混合到账拆成明确分笔并保留共同凭证引用。
6. 所有案件、工作台、财务、客户、报表及导出统一调用财务口径服务，不在页面各算一遍。

### 3.2 金额定义

- 有效合同额：已生效原合同及变更计算结果，不包括草稿。
- 有效应收：有效应收单本金加减已经确认的应收调整。
- 待收余额：有效应收减有效核销；未到期、条件待成就、未约定日期分别列示。
- 已确认收款、已确认退款、净收款分列；待确认款不进入这些统计。
- 律师费收入仅统计律师费类；代收款余额独立展示。
- 不继续把“本年度全部收款 / 本年度新增应收”称为回款率。提供明确的“本期应收核销率”，按同一批应收及指定统计时点计算；历史款回收额另列。

### 3.3 发票与收款

- 新增按金额记录的票款关联，使用发票申请 ID，不用发票号码字符串判断是否收清。
- 一张票支持部分收款、多笔收款；一笔款支持分配到多张同案发票。
- 待确认实收不减少发票未收金额；关联金额同时受收款可用金额和发票有效金额约束。
- 收款与应收的核销、收款与发票的关联是两种关系，不能把同一笔金额相加扣两次。
- 待开票、部分回款、已收清、后续更正分别显示；全量统计不得受列表条数和页面筛选限制。

实现位置：src/server/finance/、src/lib/finance/（新增领域目录，集中金额与状态规则）、src/server/reports/、dashboard/、clients/、财务页及案件财务组件。

## 4. 修复二：退款、折让、冲销和分成

- 退款、折让、冲销都必须关联真实原记录、金额、原因、经办人和必要凭证；记录状态为待确认、已确认、已退回/取消。
- 原账保留；更正与余额、分成、审计在同一事务内生效，重复确认只有一次有效结果。
- 退款区分“退钱但仍保留债权”和“退钱并减免对应债权”。前者解除相关核销、恢复应收；后者同时生成明确的应收减免，不一律将退款变成欠款。
- 折让只调整应收，不伪造资金流出；已收金额超过变更后应收时，形成待处理余额并选择退款或明确的预收用途。
- 冲销用于误记：反向抵销原记录及派生影响，可关联正确的新记录；不能通过负数普通实收绕过确认。
- 退款不能超过原收款扣除既有退款后的可退额；解除核销及票款关联必须明确对应项，不能盲目撤销其他正确分配。
- 分成按原确认收款产生时的方案及资金性质追溯；后续变更分成方案不重写旧分成。退款/冲销生成关联的分成调整。
- 页面区分“已计提分成”和“实际已支付”。已支付部分需要扣回时显示待扣回事项，不宣称钱已经自动收回。
- 两人不是强制前提：保留小所同一财务账号分两步登记与确认的使用方式，但每一步均留人员与时间。

## 5. 修复三：合同变更与代理范围

- Billing 保持在案件内；增加原合同/变更来源、变更类型、生效日期、变更前后金额及对应附件关联。
- “原10万追加2万”结果12万；“原10万调整总价8万”结果8万；仅延期结果仍为10万。所有计算基于明确语义。
- 保存草稿、正式签署/生效、终止结算形成可用操作；收案转化带入的收费约定不自动伪造签署日期或已生效事实。
- 程序和服务范围关联具体收费约定，标注“已覆盖”“需补充委托”“待复核”；零收费、有明确豁免的范围也可以记载，不用虚假金额绕行。
- 委托终止保留原因、时间、已完成事项和待交接事项；历史费用及未结款继续管理。
- 协议调整与应收调整使用同一更正链，防止补充协议减少一次、折让再重复减少一次。

## 6. 修复四：归档后收尾与状态协调

- 程序、律师服务、财务、归档四条状态分别呈现；结案/服务完成时列出仍开放的程序、期限、任务和保全事项，要求处理或明确说明。
- 归档提交和批准时都重新检查未完成期限、开庭、保全续封、待接管事项、待确认款、待执行审批等；变动后提示重新核对，不能只依赖提交时清单。
- 可能产生漏办的事项未落实负责人不得直接归档；已明确移交的事项可继续跟进，并固定移交信息。
- 未结清款项本身不阻止归档，必须列出余额和后续负责人；财务门禁单独允许归档后的追加业务。
- 已批准材料、当次目录、校验值和导出内容保持固定。新增的收尾材料作为补充记录，不静默进入旧归档包；需要正式补充归档时形成新的补充快照及审阅记录。
- 归档后若重新委托二审/执行等新增业务，创建有关联的新案件；本批不把“归档后收尾”变成任意重新开放并修改旧卷宗的入口。

## 7. 修复五：收案补正与申请轮次

- 在待补正收案详情与审批详情提供“修改申请”入口，复用收案表单并完整回填；允许保存修改后再重新提交。
- 只有申请人/当前收案主办及相应业务权限可编辑；团队只读与单纯审批权不能修改申请。
- 每轮送审固定申请字段、主体及附件清单；审批人查看明确的当前轮次，历史轮次保持可读。
- 修改当事人身份、角色、代理范围后旧核查不再满足当前提交条件；重新检索与结论关联新轮次。
- 仅修改备注等非关键字段不机械重跑全部流程；提交前由服务端核验字段版本、当前审批路由及冲突覆盖。
- 待审批中需要修改时先撤回到可编辑状态，审批与撤回并发只能一项成功。
- 转案件与再次提交均校验当前主办/协办有效性，不把申请创建时有效视为永久有效。

## 8. 修复六：交接与应急接管

- 当前主办可以发起交接；具 matters.transfer 专门权限者可以因离职、失联、停用等原因发起接管。
- 交接清单包含案件主办、程序负责人、未完成任务、期限/开庭责任人、在办收案、待确认款与未完成申请；逐项指定接收人。
- 正常交接由接收人确认后生效，旧负责人在接受前继续负责；历史登记、审批、分成等归属不改写。
- 停用账号仍可立即执行，不能为等交接而保留失效人员访问。停用前显示未交接清单；应急停用后立即形成接管待办，指定有效临时负责人，紧迫事项即时通知。
- 无有效临时接管人时，后台持续显示未接管风险并通知有接管资格人员；不能自动把业务权限授给超级管理员。
- 接管权限只开放必要的案件标识、责任信息和交接动作；接收人按新成员关系获得正常业务访问。
- 已完成审批/执行记录不换名字，待处理环节按当前有效路由重新检查；没有合格审批人时可见地提示配置缺口。
- 成员移除、岗位停用等其他撤权入口也检查未完成职责，避免只修账号停用一个入口。

## 9. 修复七：正式案件动态冲突复核

- 正式案件可建立专属冲突复核记录，与收案检索和无结论预检明确区分；预检仍不能替代正式核查。
- 保存当前主体及身份/角色快照、服务范围、检索时间、命中摘要和处理结论。
- 新增/变更重要主体、代理立场及扩大委托范围后，标记相应范围待复核；保留真实变更事实，不能为了审批而阻止记录法院追加的当事人。
- 新范围正式承接前重新检索；批准时检查主体版本及检索后的新增相关记录，出现新命中则要求复核，不复用过期的无命中结论。
- 新增程序如果已有有效合同覆盖，也需确认当前主体及范围未发生影响核查的变化；纯参考程序不等于新承接。
- 冲突结论权限按案件/收案当前经办和核查职责校验，不能用“可读”代替“可写”。
- 不自动将高风险命中判为可承接，也不把无命中表述为法律意义上的无冲突；跨案件披露维持原有最小范围。

## 10. 修复八：期限、开庭和提醒责任

- 期限、开庭增加责任人和接手确认；默认程序主办，缺省案件主办，仅允许有效且具访问资格的案件成员承接。
- 创建、改期、转交、确认来源等事件触发必要的即时提醒；复用 JobQueue 做持久投递、失败重试和去重。
- 保留定期扫描作为补漏，并在进程恢复后补扫遗漏区间；同日紧急事项不等待次日固定扫描。
- 待确认的规则推算日期在案件、日程、订阅和通知中一致标明“待核对”；保留提醒，不把它显示成已经人工确认。
- 开庭增加改期、取消、完成状态及原因/来源；已取消安排不再提醒，历史记录和日历标识保留，避免删除重建产生重复事件。
- 期限增加调整/取消的明确路径；改期后旧投递任务失效，已经发送的通知标明被替代，并通知当前责任人新时间。
- 通知已读、接手确认、事项完成三个状态分开；未接手及逾期按有效团队/接管关系升级，升级前重新校验可见性。
- 参考程序、已删除案件、已取消事项不进入正常提醒；已归档但明确保留的收尾事项继续提醒。
- 所有日期比较、日界线、提醒文字均按上海时区；不会修改系统时区配置。

## 11. 同批补齐的其他流程

### 11.1 审批通过后终止执行

- 用章和开票增加“终止执行”路径，与驳回、已执行后的更正分开；填写原因、保留原批准记录，通知申请人。
- 待执行终止由当前具执行权限者或相应审批资格者确认；申请人可提出终止请求。终止与执行并发只允许一个有效结果。
- 已开票不能直接变成“未开票”：支持登记外部已完成的红冲/作废及替代票据，保存依据和关联，并调整票款关联与统计。系统只记录票据处理，不替代外部开票系统。
- 已盖章的材料不能按未执行取消；后续更正另留记录及替代材料，不改写原盖章历史。

### 11.2 顾问续约与成果交付（后续功能扩展，本轮不实施）

- 服务到期前产生续约/终止确认待办；续约记录新的期间、范围及费用变更，不覆盖原服务期间。
- 成果交付记录关联材料、交付日期、接收对象及确认/反馈；系统服务完成前可核对，上传材料本身不视为客户验收。
- 归档仍按现行材料核验要求；不把所有非诉案件强制要求一份并不存在的客户确认函。

### 11.3 收案阶段紧急事项

- 待审批/补正收案可登记紧急事项、日期和责任人，明确标记尚未正式承接；登记不替代冲突核查和承接审批。
- 转正式案件时沿用原事项身份和历史，转入相应程序/环节，避免重复提醒。
- 不接案或撤回时逐项明确取消、告知或移交结果；不能仅因收案终止就静默丢失紧急事项。

### C 批实施细则（2026-09-19）

收案先保存草稿，材料上传、正式检索完成后才冻结为送审轮次。待审批时不得修改申请或附件；申请人/主办可撤回后补正。每次送审固定完整字段、主体、材料清单与检索记录；转案时复核字段和材料未变化、人员仍有效，并实时重跑检索核对新增命中。仅改备注不使主体复核失效；主体身份、角色、类别或服务范围变化必须重新检索。申请内的委托方身份以收案当事人快照为准，修改不会悄悄改写客户主档或已送审轮次。

轮次快照只在原申请查阅权限内展示，不成为跨案阅读入口；历史审批资格只开放当轮固定附件。补正保存采用版本校验，与审批、撤回和转案共用授权事务锁。正式案件的动态冲突复核另绑定案件及当前主体指纹，不可引用工作区预检。主库尚未切换期间，候选功能仅在独立库验证，不宣称已上线。

### D 批实施细则（2026-09-19）

`src/server/matters/handover.ts` 管理交接事务，`src/server/reminders/responsibility.ts` 管理事项责任与状态，入口归入案件详情、收案详情及日程页，不新增一级导航。数据库记录每个任务、期限及开庭的责任人、承接时间、状态、版本和改期/取消理由。创建时默认程序主办，其次案件主办；指定给他人只通知待承接，不把已读当承接。原事项仍保持原 ID，改期、取消、办结追加审计并停用旧提醒。

案件主办变更须产生交接单，固定当次未完成程序、事项和待处理财务/审批；接收人确认且复核清单未变化后，才同时改变主办及原主办所负事项。原主办在接收前继续负责。`matters.transfer`（仅 ALL）为独立应急接管权限，不属于系统管理权或普通管理权。紧急接管必须说明理由，立即明确新责任并要求承接确认。移除成员前检查其尚未完成事项；账号/岗位停用立即撤权，同时形成持续可见的待交接风险，不以交接未完成阻止安全停用。

收案紧急事项独立保存责任人、时间、状态及处置说明；转案只补充正式案件关联，保留同一事项 ID。拒绝接案前须明确办结、取消或后续处置并告知，不静默消除到期风险。

### E 实施细则：归档关闭核对与追加收尾

归档前在案件内保存服务完成说明、完成日期和财务收尾责任人，固定程序、事项、保全及财务/审批余额清单；提交与批准都重新读取并比较。未结束的程序、事项、保全、未接收交接以及待确认收款、待执行审批须先处置；转由其他案件继续办理的事项应在新案件落实并在原事项写明移交后结束。未结应收、未分配收款及分成余额可以保留，必须指定仍有效且具独立 `finance.tail` 权限的后续负责人。该权限不随系统管理或普通财务岗位取得，且不能新签合同或承接新业务。

### 审批终止实施细则

批准记录保留原状态与原批准人，执行终止另立追加记录。申请人或当前有权执行/审批者可说明原因申请终止，当前执行人或审批人确认；申请人本人不能确认自己的终止申请。待核实终止期间暂停开票/盖章，退回或撤回终止申请后才能恢复执行。终止确认与实际执行使用同一事务锁及当前状态检查；已经开具或盖章的记录不能终止，只能走实际执行后的更正流程。审批工作台显示“终止待核实”“已终止执行”并保留全部处理历史。

在办收案交接采用独立交接单，同样要求普通接收或专门应急授权；固定收案版本及紧急事项。交接更换当前主办，不改历史登记人；待审批收案退回可编辑状态，按新主办重新提交，既有送审轮次不改写。紧急事项同时转交，新主办承接后再转正式案件。

已开具发票的红冲、作废、换开采用独立更正记录：原票号码、金额、文件与批准记录不覆盖；记录实际外部处理日期、凭证编号及本案依据文件。红冲可部分，作废和换开须处理全部剩余票面金额。换开关联本案已开具新票。必要时明确解除原票的票款关联，保持已关联金额不超过更正后票面净额；不因此产生退款或改变实收、应收核销。
