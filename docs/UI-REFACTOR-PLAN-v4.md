# LawLink UI v4 重构方案

> 状态：基础层实施已于 2026-08-23 获确认；业务页面迁移仍按批次验收
> 前置依据：`docs/UI-AUDIT-v4.md`

## 一、目标与非目标

### 目标

- 建立适合律师高频工作的统一界面语言；
- 用少量页面母版覆盖大部分业务页面；
- 让视觉修改与权限、状态机、数据访问解耦；
- 保留现有真实功能和高信息密度；
- 建立可重复执行的浏览器验收流程。

### 非目标

- 不重写数据模型、Server Action 或权限系统；
- 不把项目迁移到 Sites、共享 SaaS 或新的部署平台；
- 不为了视觉整洁删减收案、案件程序、财务、审批和归档能力；
- 不在第一阶段追求全站一次性统一；
- 不以静态 mockup 或单张截图代替真实交互验收。

## 二、v4 设计原则

1. **任务优先**：首屏先回答“现在要处理什么”，统计和装饰退居其次。
2. **上下文稳定**：案件名称、程序、状态和关键期限在工作过程中保持可见。
3. **密度分级**：列表可以高密度，录入区必须留出防误操作空间，设置页不必模仿数据表。
4. **一层一个重点**：页面级只保留一个主操作；卡片、颜色、徽章不得同时竞争注意力。
5. **颜色有法律后果**：红色只表达风险或阻断，绿色只表达完成，teal 只表达品牌和当前交互。
6. **真实数据先行**：所有原型使用现有字段、真实中文长度和异常状态，不使用理想化占位结构。
7. **渐进迁移**：先抽 pattern，再替换页面；禁止整页重写复杂业务组件。
8. **Apple 式克制**：直接反馈、系统字体、轻量材质和空间一致服务于高频法律工作；不做 macOS 外观复刻，不用全站玻璃或装饰性弹簧。

## 三、信息架构与页面母版

### A. `CommandDashboard`

用于工作台。结构固定为：

1. 今日行动与风险；
2. 待审批、待补正、期限、开庭等短周期事项；
3. 案件与经营概览；
4. 趋势和分布。

空状态不得保留与有数据时相同的首屏高度。

### B. `DataIndex`

用于案件、客户、财务流水、审批、归档、报表列表。结构固定为：

1. `PageHeader`；
2. `SegmentedNav`；
3. `ListToolbar`：搜索、筛选、排序、列设置；
4. 数据区；
5. `PaginationBar` 或游标状态。

同一筛选不得同时出现在分段导航和筛选器中。

### C. `MatterWorkspace`

用于案件详情。结构固定为：

1. `MatterContextHeader`：名称、状态、案由、客户、主操作；
2. `MatterSignalStrip`：期限、开庭、收费进度和其他关键风险；
3. `ProcedureSwitcher`；
4. `StageNavigator + StageWorkspace`；
5. 可折叠 `MatterUtilityRail`。

团队、重要事项、审批和财务进入辅助栏，但辅助栏默认只展开与当前环节最相关的一组。

### D. `TransactionForm`

用于收案、开票、用印、归档申请和复杂编辑。结构固定为：

1. 标题、状态和完成度；
2. 锚点或步骤导航；
3. `FormSection`；
4. 顶部错误汇总；
5. 固定提交区。

连续表单默认优先于强制分页向导；只有步骤之间存在明确校验依赖时才拆成 wizard。

## 四、组件边界

代码阶段开始前，先修改 `AGENTS.md` 目录约定并新增：

```text
src/components/
├── ui/          # shadcn 原子组件，不承载 LawLink 业务视觉
├── patterns/    # PageHeader、Toolbar、StatusBadge、FormSection 等跨页面模式
├── layout/      # AppShell、Sidebar、Topbar
└── <domain>/    # matters、finance、archive 等业务组合组件
```

首批 pattern：

- `PageHeader`
- `PrimaryAction`
- `SegmentedNav`
- `ListToolbar`
- `StatusBadge`
- `RiskIndicator`
- `MetricStrip`
- `DataRow`
- `FormSection`
- `FormErrorSummary`
- `EmptyState`
- `MatterContextHeader`
- `ProcedureSwitcher`
- `StageNavigator`
- `UtilityRail`

## 五、实施阶段

### 阶段 0：保护基线

- 不处理当前工作区既有修改；
- 代码实施前确认当前真实内容改动的归属；
- 在独立 `codex/ui-v4` 工作区进行 UI 重构；
- v4 获确认前，`docs/UI-DESIGN.md` 继续保持 v3.3 为当前执行版。

### 阶段 1：设计系统与壳层

先改文档，再改：

- 语义 token；
- 字号、间距、圆角和阴影阶梯；
- AppShell、Sidebar、Topbar；
- Button、Input 等原子层与品牌 pattern 的职责边界；
- 状态、风险和图表配色映射。

交付门：登录页和空壳页面通过 1440/1280/390 检查。

### 阶段 2：四个代表页面

依次迁移：

1. 案件列表；
2. 收案登记；
3. 案件详情；
4. 工作台。

顺序理由：先建立列表和表单 pattern，再处理最复杂的案件详情，最后让工作台复用已经稳定的指标、风险和列表模式。

### 阶段 3：业务扩展

按 pattern 类型批量迁移，而不是按路由随意挑页：

- `DataIndex`：客户、财务、审批、归档、报表；
- `TransactionForm`：开票、用印、归档、设置表单；
- 详情类：客户详情、收案详情；
- 专项页面：日程、法院短信、冲突检索。

### 阶段 4：无障碍与响应式收口

- 键盘导航和焦点顺序；
- 颜色对比与非颜色状态提示；
- 中文日期、金额和长文本；
- 390px 移动端最小可用流程；
- 200% 缩放下的关键操作；
- 打印样式回归。

## 六、Figma 与插件的角色

Figma 插件是可选项，不是前置依赖。

若接入 Figma，只建立一个 LawLink 文件：

- Variables：颜色、字体、间距、圆角；
- Components：与 `patterns/` 一一对应；
- Canonical pages：工作台、案件列表、案件详情、收案登记；
- States：空、加载、错误、权限不足、超长文本。

项目文档和代码 token 仍是约束来源；Figma 不得形成另一套脱离实现的规范。

## 七、每批改动的验收门

每一批只包含一个可审阅主题，并依次完成：

1. 文档与目录规则更新；
2. 代码修改；
3. lint、typecheck、Prisma 校验、生产构建；
4. 确认 3000 端口属于 LawLink；
5. 真实浏览器检查代表页面；
6. 检查长名称、空数据、逾期、权限不足等异常状态；
7. 记录仍未迁移的旧样式，不用临时覆盖掩盖。

## 八、下一决策点

开始业务代码前，需要确认两件事：

1. 是否接受 `src/components/patterns/` 与原子组件职责调整；
2. 当前工作区的实际内容修改如何保留到 UI 分支。
