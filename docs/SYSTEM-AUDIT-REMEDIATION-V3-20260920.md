# LawLink 全系统问题与解决方案 v3：以法院短信办案流程为重点

日期：2026-09-20。状态：供叶森审阅的设计建议；不是已完成清单，不改变现行权限，不构成本轮 Schema、迁移执行、删除或发布授权。

依据：`SYSTEM-AUDIT-20260920.md`、本任务前两轮源码及本机结构核验、用户本轮对法院短信的产品要求，以及本轮短信入口、取件、AI、材料抽取和数据模型复核。此前数据库核验和 26 项测试属于前轮结果，本轮未重跑数据库核验或业务流程。原报告未附明细的约 30 项 P3 不视为已全部核验。

## 1. 总体判断与目标

法院短信应升级为核心办案入口：粘贴一次，系统尽可能完成取件、阅读、案件匹配、程序与环节归类、事项生成建议和档案修正建议，律师集中核对后应用。权限修复必须支持这一流程，不能把所有跨案分诊一刀切封死。

全系统同时保持四条底线：

1. 来源原件、AI 提取结果、律师确认结果分别保存，任何一步均可追溯。
2. 自动处理尽可能充分，正式业务变更只在有权确认后生效；紧急来件在待确认期间仍提醒。
3. 案件、程序、环节、材料、事项复用同一套业务对象，短信不另造一套案卷或日程。
4. 失败有状态、有责任人、有重试或人工接续出口；“已下载”“已阅读”“已整理”“事项已办结”不是同一个状态。

## 2. 当前短信能力与实际缺口

以下是本轮直接阅读当前实现得到的结果，不把历史 PRD 的目标当成现状。

| 能力 | 当前实现 | 主要缺口 |
|---|---|---|
| 粘贴与批量 | 有粘贴弹窗、正则预览、空行拆分 | 空行可能属于同一短信；需要拆分预览和合并修正，避免误拆 |
| AI 解析 | `sms-parser-ai.ts` 只补摘要、律师动作、紧急程度，输入截取前 1500 字 | 不是附件理解、字段提取或自动整理；失败降级需可见，不能显示为完整分析成功 |
| 案件匹配 | 用短信案号 `findFirst` 匹配；未匹配时不能提取附件 | 无唯一性确认；案号可能只存在链接内文书，形成“先有案件才能取件”的循环 |
| 程序匹配 | 找不到对应案号时回退到首个代理程序 | 多程序案件容易放错；不能用第一个程序替代真实判断 |
| 链接取件 | 支持直链、HTML 中有限的文件链接、重定向、部分错误状态 | 单页面候选最多 5 个，找到首个成功文件即返回；不能代表全部取件 |
| 复杂平台 | 识别登录、验证码、签收等提示 | 没有完整的人工接管后继续下载、再送入 AI 的流程 |
| 材料归类 | 按短信类型、文件名设材料类别，写入案件及程序 | 没有读全文决定类型；未落实环节 `stageId`；未匹配案件缺少私有暂存区 |
| 文本与 OCR | 通用服务支持 PDF 文本层、DOCX、文本；扫描 PDF 标为跳过 | 通用扫描件 OCR 未完成；短信下载路径未串接通用文本抽取；传票识别是分立入口 |
| 案件修正 | 有从短信补入空白案号的入口 | 没有来自短信及附件的统一字段差异、版本校验、律师确认和纠错链 |
| 事项 | 一条短信各保存一个开庭 ID、一个期限 ID | 一条短信多附件、多期限、多案件难以表达；当前生成过程分段写入，并发和部分失败需处理 |
| 处理状态 | 以 `processed` 布尔值及人工标记为主 | 无法表达部分文件失败、材料已整理但关键事项待确认等状态 |

主要依据：`src/server/sms/actions.ts`、`src/server/sms/attachments.ts`、`src/lib/sms-parser-ai.ts`、`src/lib/documents/text-extraction.ts`、`src/server/ai/parse-summons.ts`、`src/app/(app)/inbox/_components/sms-paste-dialog.tsx`、`prisma/schema.prisma`。

## 3. 律师实际使用流程

### 3.1 一次粘贴，后台完成准备

1. 顶栏法院短信入口点击“粘贴短信”，粘贴原文。多条时先展示拆分结果，允许合并或调整。
2. 点击“提取并整理”。在本所已明确配置的处理策略下自动启动取件、解析和匹配；AI 未配置仍能保存、取件和手工处理。
3. 原始短信先成功保存，耗时工作进入现有任务队列；律师可以离开页面，进度持续显示。
4. 新来件先作时间敏感信息扫描，有明确紧迫日期或待核紧急内容时先通知，不等待全部附件分析结束。
5. 系统形成一个“本次整理结果”：匹配案件与程序、文件去向、拟新增/变更事项、拟修正字段、未完成问题。
6. 律师查看来源、修改建议，点击“确认并应用”。同批无冲突的整理可一次确认，高影响或相互矛盾项目须明确选择；不要求逐份文件重复开弹窗。

### 3.2 确认界面

桌面左侧原文/原件预览，右侧整理结果；窄屏上下排列。主按钮只有“确认并应用”。

结果按四块组织：

- **归属**：案件、程序、环节及匹配依据。不能唯一确定时让律师选，不默选首条。
- **文件**：每个文件的完整状态、识别名称、文书类型、建议环节、是否重复及原页定位。
- **事项**：新增开庭、举证/缴费/补正等期限、其他任务；展示日期来源、负责人及是否待核。
- **档案修正**：原值 → 建议值 → 原文位置；允许采用、修改或拒绝。待确认内容直接预填，不让律师重新抄录。

“默认修正”的实现含义：系统自动形成完整的变更草稿，并在相关案件位置显示“待确认建议”；确认前不覆盖正式值，不被正式模板、财务统计、正式导出或冲突结论当成已核实事实。案件匹配可靠且有相应访问资格时，可在建议环节展示待整理来件；不可靠时仅留在私有来件区。

### 3.3 示例（合成场景）

一条短信包含一个送达链接，链接内有受理通知书、传票和举证通知书。系统应：

1. 列出 3 个文件，逐个取件；其中一个失败时显示“已取得 2/3”，不报全部成功。
2. 综合文件案号、法院、当事人确认对应案件及一审程序。
3. 受理通知书建议进入立案环节，传票进入开庭环节，举证通知书进入举证环节；不存在的环节仅提出创建建议。
4. 预填案号、法院、受理日期及联系方式；传票形成待确认开庭，举证通知形成待核期限。
5. 如正式档案已有不同案号、时间或主体，显示冲突并要求选择，不能按“新文件更晚”自动覆盖。
6. 律师一次确认后，正式材料、事项、字段及经办记录按同一处理批次落地；原件及原值仍可追溯。

## 4. 取件能力：不限于公开 PDF 直链

### 4.1 未匹配案件也能先取件

原始短信和下载文件先进入收件人/受托分诊人的私有来件暂存范围。取得文件后再从正文提取案号和当事人，解决短信只有“请点击查收”时无法匹配的问题。

未匹配文件不进入全所检索、其他案件材料或普通归档；确认归属后再正式关联。保留原始文件名、来源、内容校验值、取得时间和处理人，显示名可另行规范化。错误归属可经有权人纠正，但不得抹掉原处理历史。

### 4.2 平台按能力分层

| 情况 | 处理方式 |
|---|---|
| 已确认无额外签收动作的文件直链/公开取件页 | 自动下载全部可识别文件，逐件记录 |
| 常用平台且取件流程已验证 | 配置平台适配器，识别文件清单、分页及必要跳转；支持版本化测试 |
| 登录、验证码、实名核验或明确签收 | 打开受控浏览器交由律师完成必要步骤；随后接回文件及后续整理流程 |
| 暂不支持的平台、小程序或访问失败 | 保留来源与错误，支持律师下载后拖入“补充本次来件”，接续相同分析流程 |
| 链接过期、密码错误、文件数量不明 | 保持“待处理/部分完成”，提供重试、补传、联系法院等处置记录 |

不能承诺一个通用抓取器自动处理全部法院平台。首期应以用户实际高频平台的获授权样本选择适配顺序，平台覆盖清单与限制明确展示。

平台可能记录访问、查看或签收动作；不把“请求为 GET”自动等同于没有业务效果。首次接入时确认平台行为，显式签收、提交陈述、缴费等动作保留给律师。粘贴时间、文件取得时间、文书落款时间、平台签收时间分别记录；不把它们自动等同于法定送达日。

人民法院送达平台公开登录页实际包含证件号码与通知中的六位验证码输入，可证明受控登录是实际需求，不应把登录失败当作终点。来源：https://songda.court.gov.cn/wscx/dsrlogin.html （本轮读取）。这不是对全部平台认证方式的概括。

### 4.3 完整性与重试

- 一个链接可以包含多份文件，一个文件可以含多种文书；文件层保留原件，文书层按页段分析，不破坏原 PDF。
- 压缩包保留原包，安全解包并记录成员清单；限制数量、解包体积与路径。无法读取或加密成员单独列明。
- 同内容去重不能去掉再次送达这一事件；同文件的不同短信/送达批次保留各自来源关系。
- 同名但内容不同的文件不得当重复文件跳过。改期、撤回、补充材料形成新的来源事件及关联建议。
- 去重与幂等由服务端及数据库约束共同保证，不能只在写入前查一次。
- 下载超时要覆盖响应体；按流限制体积，不能只依赖 Content-Length。平台页面数量未知时显示“完整性待核”，不能把找到的数量当成全部。
- 每次重定向、实际连接目标及下载内容均作校验；防止链接访问内网、危险文件或解包路径越界。平台标识不能仅靠 URL 里出现 court/12368 等文字认定。
- 原始链接中的验证码、令牌及登录会话独立保护，不进入普通审计详情、AI 提示或公共分享；必要的完整来源保存在受控记录中。

## 5. AI 阅读、分类与案件信息修正

### 5.1 处理顺序

文件类型核验 → 文本层提取 → 无文本层时 OCR → 页级/文书级分析 → 字段与事项提取 → 规则校验 → 与现有档案比对 → 形成建议。

通用扫描件 OCR 是短信首个可交付版本的必需能力，不能把已有“传票图片识别”当作已完成。PDF 混合文本页和扫描页按页处理；页数、失败页、截断范围必须可见。长文按页段提取后汇总，不能只截取首页或前若干字符并宣称全文分析。

AI 可以判断文书类型、建议环节、提取事实、摘要及需要律师行动的内容，但不能直接调用案件写入或权限变更。短信、网页、附件中的指令都作为待分析内容，不作为系统命令。

### 5.2 每项建议的最少信息

记录目标案件/程序/环节、目标字段或事项、原值及原版本、建议值、文件及页码/原文片段、提取方式、冲突原因、确认状态、确认人和时间。AI 置信表达是辅助信息，不能以一个自报百分数替代案号唯一性、来源定位和逻辑校验。

律师点击字段即可回看相应原页。无法定位原文的关键建议不得预选为可直接采用。拒绝过的建议重跑后不重复弹回，除非出现新来源或来源内容变化，并说明变化。

### 5.3 分类与修正规则

| 内容 | 系统自动准备 | 正式生效条件 |
|---|---|---|
| 文书类型、显示名称、摘要 | 根据全文及标题预填；保留原始文件名 | 随本次整理确认，允许改分类 |
| 案件、程序、环节 | 按案号、法院、主体和上下文匹配候选 | 唯一可靠匹配且确认人有权；不明时人工选 |
| 空白案号、法院、受理日期、法官联系方式 | 自动填入建议值并展示原文 | 本案有权律师确认 |
| 已有字段修正 | 新旧值并列，展示来源及冲突 | 明确选择采用/保留/修改；检查当前版本 |
| 主体名称、信用代码、身份、代理立场 | 提出变更，不直接更改客户主数据 | 有对应编辑权限，查重；重要主体变化触发动态冲突复核 |
| 新程序、二审/执行信息 | 提出新增程序或关联新案件建议 | 人工确定；不自动承接，不自动标为办理中 |
| 开庭及指定日期事项 | 生成待确认事项、负责人建议 | 律师确认；待确认期仍按紧迫性提醒 |
| 从起算事实推导期限 | 保存依据、起算事实、规则版本和待核结果 | 所需事实齐备并经律师核对；不由 AI 凭印象计算 |
| 财务通知或缴费要求 | 保存通知及缴费待办 | 不自动记支出、收款、到账或核销 |
| 判决/结案/归档相关内容 | 摘要和建议下一步 | 不因收到裁判文书自动结案、归档或认定履行完毕 |

程序与环节分别处理：一审/二审/执行属于程序，立案/举证/开庭等属于其内部环节。材料类别也不是环节。正文包含多个案号时，区分当前案号、前审案号、关联案号和引用类案号，不以“发现一个案号”直接归案。

### 5.4 正式应用与纠错

正式应用前，在事务内重新校验人、权限、案件状态、原字段版本及来源版本。同一处理组的字段、事项、材料归属和审计原子提交；文件抓取与 AI 请求不占用长数据库事务。不同案件的处理组分别确认和提交，部分完成情况逐组显示。

发生并发修改时展示新的差异，不用旧提取结果覆盖律师已改内容。误确认后追加纠正记录并检查依赖；不简单把所有字段回滚到旧值，以免覆盖后续合法修改。改期应更新同一开庭事件并保留历史、撤销旧提醒，不能另造第二个看似独立的开庭。

### 5.5 已确认的内容范围

叶森已明确“短信录音”为口误，本次范围为短信文字及链接文件。不纳入音频、通话录音、语音转写或说话人分析，不让音频能力影响本次短信文书流程的交付。

## 6. 权限、责任与确认：为分诊提供明确通道

### 6.1 权限矩阵建议

| 动作 | 建议范围与约束 |
|---|---|
| 粘贴本人收到的短信、保存原文及自己的来件文件 | 本人或明确受托的收件人员；未匹配案件也允许 |
| 全所来件分诊 | 经明确配置的管理/分诊人员；行政可单独获得分诊资格，不必同时取得全所财务和案件正文权限 |
| 为非经办案件准备整理建议 | 可授权分诊人处理本次来件及最小匹配信息，不开放该案其他材料、全文和财务 |
| 将建议正式应用到案件字段或事项 | 默认由当前主办、协办及明确具有相应办理权限的律师确认；权限依操作性质校验 |
| 换材料版本、主体变更、承接新程序 | 沿用相应办理/材料/承接权限，分诊资格不能替代 |
| AI 外发 | 校验本次来件/材料的全文处理资格及 AI 使用授权；单纯审批阅读权、管理读取权不自动取得外发资格 |
| 单人执业 | 同一人可录入和最终确认，但仍记录两个阶段；不能套用强制另找一人审批 |

这是建议建立的受控分诊通道，不是宣称现有管理权已授权跨案写入。实施前在 AGENTS/PRD 明确范围。内部按动作白名单执行，不引入可任意配置每个字段的复杂权限矩阵。

### 6.2 责任归属

事项负责人从当前有效程序主办、案件主办中建议选定，并验证本案访问及承担资格。分诊人保留经办记录，但不自动成为法律事项负责人。找不到有效负责人时形成待接管事项和紧急告警，不静默丢弃，也不将失效账号当作已落实责任。

AI 尚未确认的紧迫开庭/期限在工作台、案件、日程和订阅出口使用一致的待核标记；通知不得写成已核实结论。不明日期先催办“核对来件”，不编造到期日；相互冲突的日期同时展示并紧急核查，不悄悄取消原正式提醒。

收到提醒不等于承接责任。普通交接需新负责人确认；应急接管使用独立权限。停用或撤权不等待交接，但会持续显示未落实责任。

### 6.3 完成语义

取件、分析、确认分阶段记录；来件可表现为处理中、待人工取件、待匹配、待确认、部分完成、已整理、无需处理。

“已整理”表示所有应处理来源已取得或有明确处置、建议已确认/拒绝、所需事项已建立。它不意味着这些待办已经办结。原来的“标记已处理”保留为人工处置入口，但有未解决附件或紧急事项时需明确说明其去向，不得让角标消失掩盖遗漏。

## 7. 其他系统问题的统一解决原则

- **权限与 AI**：读取、分诊、办理、材料、财务、导出分别判断；不靠从权限列表减掉 MANAGER_GRANTS 推导写入权。保留各入口的主办/成员限制，不新增合伙人通用写入豁免。
- **程序门禁**：`updateProcedure` 明确事务化；事务内复核状态与权限，协调合同/主体/范围变更锁或版本，拒绝后零写入。已办理程序扩大范围也须复核；真实事实登记不能被门禁阻断。
- **日期**：全天业务日按上海口径，ICS 格式为 YYYYMMDD；开庭为具体时间点。修所有输入和出口，不靠容器 TZ 修补。已有浏览器本地午夜数据不能保证出口转换即恢复，未经证据不迁移或宣布修正。
- **归档**：原包和原快照固定，当前收尾独立维护，补充归档冻结自己的当次材料及财务截止口径。正常尾款不要求修改原包；待确认款、更正、失效负责人仍阻断应阻断的审批动作。
- **收尾交接**：正常由有效原负责人发起、新 tail 持有人接受后生效；应急由 matters.transfer 持有人指定有效人并要求承接。只交责任，不隐式授予确认到账、财务更正或分成结算权。
- **提醒**：即时评估＋持久队列＋按遗漏区间重评估＋责任断链处理。补告稳定去重，事项改期形成新版本；未到期但错过提前提醒的事项也处理。
- **法人章**：审批与回填分别授权，都核对当前法定代表人及 requiresLegalRep 条件；本人例外只解除本人操作限制，不绕过事项授权或实际用印证明。自确认清单仍硬排除法人章。开关名称必须准确反映允许本人审批/回填，不能声称自动验证单人所。
- **终止自决**：UI 与执行端共用资格计算，执行时重查第二名合格人；撤回、拒绝、确认均保留记录并解决恢复路径。
- **财务**：扣回上限按 recoverable；旧开票入口委托完整校验，缺参数明确报错。退款与免债默认按原核销对应，跨应收减免明确作为独立更正，不混成隐式选择。
- **单人主线**：向导生成明确的岗位、审批、确认、执行和收尾配置清单；独立权限可显式选择，不能暗中授予。缺 finance.correct、finance.settle、archive.supplement、交接资格时展示后果。自确认选项要么真正接通，要么明确禁用，不只警告。
- **统计**：同批应收计算核销率，约定新增应收的入期口径、折让/退款、期后确认及分母为零；业务发生日和系统确认日分别保留。当前核销金额会累加更新，须审计逐次核销历史是否足够，不足再补明细，不能只用创建日推导历史。
- **操作效率**：分配建议按付款指定用途优先，同案同类款项，无指定时按到期顺序；预览后确认。在办导出逐件校验权限并固定清单。批量办结只针对人工选定的低风险运营事项，排除期限/开庭/保全。
- **数据加固**：复核四项外键 RESTRICT、实收默认待确认及显式拒绝 AuditLog DELETE 的触发器方案。单个触发器不等于全面防篡改。SQL、影响、演练和备份方案先展示，执行另获授权。

## 8. 原审计问题逐项去向

批次 A＝先修严重错误与共用基础；B＝短信完整流程及提醒；C＝恢复能力和单人主线；D＝统计及效率。不能把“已有代码”或“测试通过”标为业务验收完成。

| 编号 | 核验/修订判断 | 处理及批次 |

| P1-1 | 只读管理范围进入写断言属实；短信不应被一刀切 | A 收敛通用写权限；B 建有限分诊及律师确认通道 |
| P1-2 | AI 全文外发范围过宽 | A 逐件全文与外发资格；B 来件 AI 使用同一边界 |

| P3 汇总 | 原报告只列举部分，未附全部域报告 | 建立逐项待核清单；无证据不报已修复，不阻塞已明确的首批问题 |

## 9. 实施顺序与每批交付

### A. 先消除严重错误，建立短信可复用的基础

处理权限/AI、程序事务、日期、法人章、超额扣回、旧开票入口、日历搜索权限；让责任失效首先变得可见；完成数据库加固 SQL 的审阅准备。短信原有入口和必要操作保持可用，不以临时全面封禁替代设计。

交付：权限矩阵、迁移候选及影响、关键拒绝/回滚/并发用例、现有主线不退化验证。A 是 B 的短前置，不要求全系统美化完成后再做短信。

### B. 法院短信专项：核心交付

B1：可靠收件和取件。原文即时保存、私有暂存、多链接多文件清单、后台队列、状态、去重、人工登录/补传接续。通用取件＋优先高频平台的首个验证适配器。

B2：读材料和形成建议。PDF 文本/扫描 OCR、分页依据、文书类型、案件/程序/环节匹配、冲突和来源定位、完整变更草稿。

B3：确认与执行。律师一次确认、权限和版本复核、正式字段及事项原子应用、改期更正、待核紧急提醒、失效责任接管、日程与 ICS 一致性。

三段合在一起验收，只有 B1 下载功能不算完成短信目标。本次内容范围按用户澄清限定为短信文字及链接文件。

### C. 流程恢复和单人完整主线

处理归档/尾款/补充归档、收尾交接、终止自决、初始化组合角色、审批配置、收案命中及草稿作废。确认导向的短信流程作为空白安装主线验收的一部分。

### D. 历史统计与办案效率

处理同批核销率及逐次事件、分配建议、在办打包导出、案件内财务操作、人工批量处置和成本指标。前期整理后的来件材料必须能随案导出，来源链一起带走。

## 10. 技术组织与拟议数据变化

保持现有单体应用和任务队列。沿用 `src/server/sms/` 编排、`src/lib/` 纯规则、`src/server/documents/` 文件处理、`src/server/reminders/` 提醒、`src/app/(app)/inbox/` 页面。不新建微服务、独立审批系统或另一套案件事项库。

最少应表达以下持久关系，确切表名及 SQL 在模型设计阶段确定：

1. 短信原文与导入/实际收到时间、平台/送达元数据；有证据才记录实际送达时间。
2. 来件来源 → 多个链接/文件 → 文件内文书页段；一份文件的多次送达来源。
3. 取件/抽取任务状态、失败原因、恢复游标、来源版本与幂等键。
4. 一次分析的字段/分类/事项建议、来源定位、旧值版本、决定及正式产物映射。
5. 一个来件关联多项任务/期限/开庭及必要时多个案件；不继续用一条短信两个单值产物 ID 表达全部流程。

原则上需要 Schema 设计，不能只把所有状态塞入一块 parsedJson 后依靠 UI 猜测。是否新增表、枚举及索引必须先形成模型与迁移影响清单，再按红线审批；本文件未执行这些变化。

## 11. 验收：以律师能否完成工作为准

| 场景 | 必须达到的结果 |
|---|---|
| 仅短信、无链接 | 保留原文，提取事实和事项，能人工确认 |
| 短信无案号，案号在文书中 | 先取件再匹配，不要求先手工建错案 |
| 一个链接至少 3 个附件 | 全部列明并逐件处理；故障明确显示，不能首件成功就结束 |
| PDF 含文本页及扫描页 | 所有页都有处理状态，关键字段可回看原页 |
| 一个 PDF 包含多种文书 | 原 PDF 保留，分类与事项按文书页段区分 |
| ZIP、同名异内容、重复送达 | 清单完整；不同内容不覆盖；重复文件不重复存但送达事件保留 |
| 验证码/登录/签收平台 | 有人工接续，完成后仍能自动分析，不让律师重新建一遍材料 |
| 未知/过期链接 | 明确失败与人工出口；原文及已有文件不丢失 |
| 多案号、多个候选案件/程序 | 不自动选首条；不向无权人披露其他案件正文 |
| 同案多个环节、环节不存在 | 建议正确去向；新增环节只在确认后建立 |
| 原字段已有不同值 | 对照显示，不静默覆盖；并发修改后要求重核差异 |
| 改期开庭 | 更新对应事件，历史可追溯，旧提醒失效，不重复生成两个开庭 |
| 临近期限但 AI/下载仍未完成 | 先发待核告警，律师可直接人工处理 |
| 程序/事项负责人失效 | 有效链路获提醒并产生持续待接管，不发给失效人后算成功 |
| 非经办行政分诊 | 可处理获授权来件，不能藉此下载整案或修改正式业务 |
| 只持审批附件阅读资格 | 不能自动获得全文 AI 外发权 |
| 重复粘贴、双击、两个并发请求、队列重试 | 不重复正式事项、字段变更或文件；重复来源关系可追溯 |
| 归档案件收到新的来件 | 仍能保存和告警；按补充归档或新增关联案件处理，不自动重开旧案 |
| 参考程序收到新通知 | 不暗改为正式承接；来件待核告警可见，正式事项按确认范围建立 |
| AI 不可用、输出缺字段或不合结构 | 保存/取件可用；明确降级，人工编辑后走同一确认路径 |
| 来件中的文字要求系统忽略权限或外传 | 只作为文书内容处理，不执行其指令 |
| 单人从空白安装开始 | 经明确向导配置走完收案、收短信、确认、办案、财务、归档 |
| 历史金额与当前金额 | 指标能下钻对应期内同批应收及逐次核销/更正，不只检验总额 |

业务测试使用合成样本；真实法院平台样本另经授权并避免自动签收。记录每个平台/文件类型的成功率、漏件率、错案率、关键日期错误、人工纠正比例和平均确认操作量；真实样本未覆盖的平台不能宣传为已经支持。

实现后的工程验证按各批改动运行 lint、typecheck、test、prisma:validate、build，并在属于本仓库的本地服务上走实际页面。数据库回滚与幂等用例需在独立库验证，不能用仅模拟函数调用的测试替代。方案文件本身不等于这些验收已完成。

## 12. 本轮范围与后续决定

本轮交付设计与全问题映射；未改 AGENTS、业务代码或 Schema，未执行迁移、真实短信取件、外部 AI 发送或法院平台签收。

已经明确的用户目标：保留并重点建设粘贴短信；提取短信和链接文书；结合 AI 分类、归入案件环节、准备案件信息修正，并由律师最终核对。

本方案推荐“自动生成完整变更草稿＋律师集中确认后生效”，实现尽量少录入、少跳转，同时保证错误不会先扩散到正式档案和期限。分诊授权、本人回填例外、收尾交接及数据库变更在实施文档中按最终确认口径分别落地，不能把本轮设计审阅记录成已批准执行。

补充来源：最高人民法院知识产权法庭 2023-03-08 发布电子送达文书司法链核验说明（https://ipc.court.gov.cn/zh-cn/news/view-2225.html）。可据此提供核验入口并保存实际核验结果，但本地 SHA256、AI 识别或“链接看起来像法院”不等同于完成官方真实性核验；本轮未验证该平台的自动核验接口。
