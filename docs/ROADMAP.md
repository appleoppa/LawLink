# LawLink 产品路线图

> 最后更新：2026-08-15（v1.2）
> 性质：说明 LawLink 打算做什么、**不打算做什么**，以及为什么。不是排期承诺。
>
> 本文档面向两类读者：评估是否采用 LawLink 的使用者（想知道某个功能会不会有），
> 以及打算贡献代码的开发者（想知道哪些方向已被明确排除，避免白做）。

---

## 一、判断依据

LawLink 从 v0.5 走到 v0.47，主线功能已齐：收案审批、多程序案件、程序工作台、财务开票、归档审批、法院短信解析、财产保全（三层模型）、文书模板卷宗、用章审批、AI 三件套（案由推荐/文书审查/类案检索）、报表。**广度不缺，缺的是深度和触达。**

两条原则支撑本路线图的取舍：

1. **目标用户是独立律师和 1–5 人小团队**（PRD §一）。这个定位决定了取舍标准：多级审批、字段级权限、强制审核流这类为大型机构设计的流程，在 5 人以下的团队里带来的摩擦大于收益，因此不在范围内。需要这类能力的团队，LawLink 可能不是合适的选择。
2. **地基先于功能**。代码体检（详见第四节）识别出的结构性问题——新旧模型并存、序列化逻辑重复、关联依赖字符串标签——会随功能数量放大维护成本，优先于新功能处理。

> 关于「哪些功能用得多」：本项目**没有任何使用埋点**，也不收集使用数据。下文对功能取舍的判断基于目标用户定位和维护成本，不基于用量统计。如果你的实际使用场景与这些判断不符，欢迎开 issue 说明——这类反馈比推测有价值得多。

## 二、下一阶段该做的模块（按优先级）

### P0 法定期限引擎 —— 最高价值，唯一「不做会出执业事故」的缺口

**现状**：`Deadline` 全靠手填，`remindDays` 手设。短信解析已能抽出「上诉期限 15 日内」这类文本（`sms-parser.ts` importantItems），但只是展示，不落库、不计算。

**为什么是 P0**：律师执业责任险理赔头号原因就是漏期限。案管系统能替律师挡住这件事，就值回全部使用成本；挡不住，其他功能做得再多也只是记事本。

**怎么做**：
1. 新表 `DeadlineRule`（规则库）：触发事件（裁判文书签收/受理通知送达/举证通知签收）→ 期限天数 → 期限类别 → 法条依据。内置规则 seed + 律所可改。
2. 触发点挂在已有动作上：程序录入「裁判签收日」→ 自动生成上诉期 Deadline（判决 15 日/裁定 10 日）；短信解析出举证期限 → 一键生成时带规则依据。
3. 每条自动生成的期限展示法条出处，可点开核对（已有元典 MCP 接入，可直接跳法条详情）。

**法律依据核验状态**（按工作区规则，写入代码前逐条过元典）：
- ✅ 已核验：上诉期——《民事诉讼法（2023 修正）》第 171 条，不服判决 15 日、不服裁定 10 日，现行有效（元典 2026-07-04 核验）。
- ✅ 已核验（2026-08-15 补核）：保全 1/2/3 年期限的正确出处是**《最高人民法院关于适用〈中华人民共和国民事诉讼法〉的解释》（2022 修正）第四百八十五条**——「冻结银行存款的期限不得超过一年，查封、扣押动产的期限不得超过两年，查封不动产、冻结其他财产权的期限不得超过三年」，现行有效，2022-04-10 施行。
  - **PRD §13.3 与 `src/lib/preservation-defaults.ts` 原引用的「民诉法第 244 条」确认错误**：该条实为执行回转（「执行完毕后，据以执行的判决、裁定和其他法律文书确有错误，被人民法院撤销的……责令取得财产的人返还」），与保全期限无关。
  - 第 485 条位于执行编。保全阶段适用同一期限的衔接路径是民诉法解释第 168 条与《最高人民法院关于人民法院办理财产保全案件若干问题的规定》（2020 修正）第 17 条——保全措施自动转为执行中的查封、扣押、冻结措施，**期限连续计算**。写 `basis` 文本时应带上这层衔接。

### P1 提醒触达出站 —— 站内提醒对不常开系统的人等于没有提醒

**现状**：通知只有站内 Popover + dashboard 卡片；cron 框架（`src/server/cron/scheduler.ts`）和到期扫描 job 已有，但提醒出不了系统。

**怎么做**（按运维成本从低到高，全部可选配置）：
1. **ICS 订阅源**：每用户一个带 token 的日历订阅 URL，开庭/期限/保全到期自动进手机日历。零第三方依赖，自部署友好，一天工作量。
2. **Webhook 推送**：企业微信/钉钉群机器人 URL 配置一条即可用，国内小所几乎都有微信群。
3. **SMTP 邮件**：可选，不强制配。

### P2 短信收件箱深化 —— 方向已对，把闭环走完

**现状**：附件提取、凭证识别、重要事项抽取已实现（v0.47）。缺的闭环：
1. **案号回填**：立案通知短信解析出新案号 → 反向回填 `MatterProcedure.caseNumber`（现在只用案号做匹配，没利用它补数据）。
2. **自动生成建议**：解析置信度高的开庭/期限，直接给「一键生成」预填草稿（时间、法庭、法官全带上），而不是让用户从头填。
3. **待人工处理队列**：`LOGIN_REQUIRED` 的电子送达现在埋在每条短信卡片里，应有跨短信的聚合视图（见第四节 parsedJson 问题）。

### P3 文书模板扩容 —— 基础设施已好，价值随模板数线性增长

docxtemplater 渲染链路、变量拼装、卷宗归档都已落地。要做的只是内容工作：预置模板从 8 个扩到 20+（PRD §11.8 既定计划），补律所自定义模板上传（v0.9 规划项）。不需要新架构。

### P4 移动端适配收尾

律师核对期限、看开庭安排的场景发生在法院走廊和路上。v0.10 做过一轮响应式，程序工作台（v0.47 新增的两栏布局）尚未适配窄屏。范围收紧为：工作台、案件详情、日程三个页面在手机上可读可点即可，不做原生 App（既定决策）。

## 三、明确不做的方向

列在这里是为了让评估者和贡献者省时间：以下方向已经过权衡后排除，提交相关 PR 前请先开 issue 讨论。**已实现的功能不会被删除**，只是不再扩展。

| 方向 | 现状 | 结论与理由 |
|---|---|---|
| **快递追踪** `ExpressTracking` | 已实现，保持可用 | **冻结，不再扩展**。依赖快递鸟 / 快递 100 的付费 API key，自部署用户通常不会单独申请；而寄件人手机上本就有物流通知。现有代码保留可用。 |
| **用章审批扩展**（自定义章种类、用章月报、统计图表） | 未实现 | **不列入计划**。现有 5 种印章 + 基础审批流程已覆盖目标规模团队的需要，继续扩展会让流程重于收益。 |
| **`CommissionPlan` 自动分成** | 已实现，v1.0 起降级 | **降为只读记录**。独立执业者没有分成场景，小团队的分成通常一案一议，自动生成分成条目反而增加对账负担。数据保留，不再在主流程中推送。 |
| **外部联系人审核流** | 已实现，v1.0 起默认关 | **改为可选设置，默认直接通过**。目标规模的团队通常不需要为添加联系人设置审批环节。需要的可在设置中开启。 |
| **客户门户 / SaaS 多租户** | 曾列入远景，现已移除 | **不做**。单实例单库是当前全部权限模型的前提；为「未来可能的多租户」预留架构弹性，会让每一处权限判断都变复杂。确有需求时更适合另起项目。 |
| **自建向量检索** | 曾列入远景，现已移除 | **不做**。类案检索已接入元典开放平台，自建向量库需要自行维护 embedding 基础设施，与自部署的轻量定位不符。 |
| **通用工时统计 / 效率报表** | 曾列入远景 | **不做通用计时器**。目标用户以按件收费为主。若顾问单位对账有实际需求，会以「顾问服务台账」这类轻量记录的形式实现。 |
| **持续的视觉改版** | 已迭代三轮 | **冻结一个版本周期**。视觉已达可用水平，边际收益递减；每轮全站改版产生数百文件的变更，挤占其他工作的评审带宽。 |

## 四、会拖后腿的数据结构（按危害排序）

### 1. 新旧两套保全模型并存 ⚠️ 最优先处理

`Preservation`/`PreservationRenewal`（旧单表）与 `PreservationCase→Target→Property→PropertyRenewal`（v0.44 三层）同时存在于 schema。**旧模型的 `src/server/preservations/actions.ts` 已无任何页面引用（经检索确认）属于死代码，却仍在随其他改动被一并维护**——维护成本正在向死代码泄漏。

**行动**：确认旧表无存量数据（或写一次性迁移脚本挪到新模型）→ 删除旧模型、旧 actions 及 dashboard / schedule 中的兼容读取。⚠️ 涉及不可逆的 schema 迁移，执行前需备份。**已于 v0.48 完成。**

### 2. `SmsMessage.parsedJson` 单 JSON 字段膨胀

解析结果、AI 增强、附件提取操作日志（attachmentResults）全塞一个 JSON。后果已经显现：`normalizeStoredParsed()` 这种版本兼容 shim 出现了；「哪些电子送达待人工处理」这类查询无法用 SQL 表达，只能全量拉出来在内存里过滤。

**行动**：附件提取结果拆成 `SmsAttachment` 子表（url/status/documentId/checkedAt），或最低成本方案——`SmsMessage` 上加 `needsManualAction Boolean` 冗余列供查询。解析结果本体留在 JSON 没问题。

### 3. 阶段↔材料靠字符串标签关联

材料归集到环节用的是 `Document.tags` 里的 `"阶段:开庭审理"` 字符串；删除环节的保护逻辑靠 `stage.name.includes("保全")`。**环节一旦支持改名，材料链接全部断掉**；同名环节跨程序也无法区分。PRD §10.2.1 自己已承认需要环节状态字段。

**行动**：`Document.stageId` 外键（可空）+ `MatterStage.status`（ACTIVE/HIDDEN）。标签方案可保留作展示，但关联关系必须是外键。

### 4. Decimal 手工序列化在每个 action 重复

本次 diff 为修 RSC 序列化在 6+ 个 action 手写 `decimalToNumber` map（finance/intakes/matters/preservations×2/invoices）。**每新增一个带金额的查询都可能漏一处，漏了就是运行时报错**，typecheck 拦不住（`Prisma.Decimal` 有 `toString`，结构上兼容）。

**行动**：收口到一处——Prisma client extension 里对 Decimal 字段统一 `result` 转换，或建立 server action 出口的统一 serialize 层。把 `src/lib/decimal.ts` 从「到处调」变成「只在一处调」。

### 5. 案由联动校验三处重复

`assertCauseAllowedForSelection` 在 createIntake / convertIntakeToMatter / createMatter / updateMatterBasicInfo 各调一次，且 `updateMatterBasicInfo` 取的是「第一个程序」的类型——若首程序是补录的 INFORMATIONAL 前序程序（如别人代理的一审），校验基准就错了。规则再变（仲裁法还会修）要改多处。

**行动**：校验基准统一为「当前 ENGAGED 的首个程序」，并把调用收口到一个入口函数。**已于 v1.2 完成，见第七节 A3、A4。**

### 6. TimelineEvent / AuditLog 手工双写

每个 server action 需要自行记录 timeline 与 audit，遗漏时没有任何提示。**行动**：中期在 service 层建立统一记录入口；短期在评审清单中列明。

## 七、v1.2 全面排查发现（2026-08-15）

一次覆盖法条准确性、权限模型、审计完整性、异步正确性的全仓库排查。**结论：未发现越权漏洞或数据损坏风险**；问题集中在法律准确性与校验入口不统一，**全部已在 v1.2 修复**。

> **如果你正在运行 v0.47 或更早版本**，A1 与 A2 会影响你看到的保全期限法条依据与到期日，建议升级后重新核对在办保全的到期时间。

### A1 保全期限法条引用错误 —— 已修

`src/lib/preservation-defaults.ts` 与 PRD §13.3 引用的「民诉法第 244 条」实为执行回转条款。正确依据为民诉法解释（2022 修正）第 485 条，详见第二节 P0。1/2/3 年的**数值本身是对的，只有出处错**。

### A2 保全到期日跨闰年算错一天 —— 已修

保全用固定天数（365/730/1095）而非日历年，与 v0.49 期限引擎的 `computeDeadlineDate` 是两套并存的日期算法。

| 场景 | 起算 | 旧算法 | 法定 |
|---|---|---|---|
| 动产 2 年 | 2027-06-15 | 2029-06-14 | 2029-06-15 |
| 不动产 3 年 | 2026-05-20 | 2029-05-19 | 2029-05-20 |

偏差方向是提前一天提醒（不会误续封），但仍属算错。**根治办法是保全期限统一走 `computeDeadlineDate(start, N, "YEARS")`，不再保留第二套日期算法。**

> 关联未办项：保全到期至今未进 `Deadline` 体系（第五节已列），仍是查询时临时拼。两件事一起改最省事。

### A3 批量导入绕过案由校验 —— 已修

`assertCauseAllowedForSelection` 有三个调用点（创建案件 / 收案转化 / 编辑基本信息），**导入路径缺失**：`src/server/imports/actions.ts` 按名称匹配后直接写 `causeId`，不做类别与程序范围校验。后果是 Excel 能导入界面创建不出来的组合（如劳动仲裁案件挂婚姻家庭类案由），且入库后编辑时才会被拦，形成改不动的存量脏数据。

第四节第 5 条原记「案由联动校验三处重复」，实为**三处重复 + 第四处缺失**，后者危害更大。

### A4 案由校验基准不区分是否代理 —— 已修

`updateMatterBasicInfo` 取 `procedures[0]`（order 升序首条），不区分 `ENGAGED` / `INFORMATIONAL`。

**可达性经核实比原判断窄**：`order` 追加式生成（`lastOrder + 1`）、无重排功能、首程序恒为 `ENGAGED`，补录的前序程序只会排在后面。要触发需先删掉原首程序。

> 更正（2026-08-15）：本节初稿写「`deleteProcedure` 无任何护栏」，**该表述不准确**。准确情况是——服务端 action 无兜底断言，但客户端有二次确认，且文案已如实告知级联后果（「该程序下的所有开庭、期限、备忘和材料记录将被一并删除，此操作不可撤销」）。级联确属实：`Deadline` / `Hearing` / `MatterStage` / `ProcedureMemo` 均为 `onDelete: Cascade` 硬删无恢复；`Document` 是 `SetNull`，材料本身不删（确认文案此处偏严）。据此该项**降级为不紧急**，见第八节。

与 A3 同一病根：校验没有单一入口。统一为「以当前 `ENGAGED` 的首个程序为基准」并收口到一个函数。

### A5 审计日志缺登录/登出 —— 已修

AGENTS.md §六 要求 AuditLog 记录「登录/登出、案件创建/查看/编辑/归档、材料下载、财务变更、冲突检索、权限变更」。实际有 130 种审计动作，覆盖度很高（`MATTER_VIEW`、`CLIENT_VIEW`、`DOCUMENT_DOWNLOAD`、`CONFLICT_CHECK_RUN`、`USER_ROLE_UPDATE` 均在），**唯独 LOGIN / LOGOUT 完全缺失**——登录成功只更新 `lastLoginAt`。对律所而言这是追责链条的起点，属合规硬缺口。

### A6 冲突检索跨案件可见 —— 确认为有意设计，已写入文档

冲突检索会把无权查看案件的案号、标题、主办律师姓名返回前端（仅隐藏链接与 matterId）。业务上必要——不跨案件检索就无法完成尽职审查，且检索人需要知道向谁核实。但这与「案件默认只对负责人、成员和管理员可见」的规则冲突，此前未在文档中说明。现已在 AGENTS.md §六 写明该例外的确切范围：案件正文、财务、材料一律不因冲突检索对非成员开放。

### 排查确认无问题的部分

- **无 IDOR**：专项扫描「用户传入的 matterId 直接写库且无任何断言」，0 处。初筛出的 28 个疑似缺可见性校验的 action 逐个复核，全部为包装函数（`requireUploader`、`assertCanAccessPreservationCase`）或作者本人校验，均误报。
- **通知 helper 防护正确**：`notifications/create.ts` 与 `approval.ts` 有意不标 `"use server"`，并注释说明「否则任何客户端可直接调用给任意用户伪造通知」。
- **期限引擎规则抽查全对**：仲裁法（2025 修订）第 72 条（撤销裁决三个月，2026-03-01 施行）、民诉法第 104 条（诉前保全三十日）均经元典核验属实，连跨法适用备注都准确。
- **材料下载接口**鉴权与审计齐全，非管理员必须为案件成员。

### A3 的实现取向修正

初版实现为「案由不合规 → 整行导入失败」。**该取向已推翻**：导入是历史数据迁移工具，历史案件按当时规则立的案由未必符合现行范围，为一个案由把整条案件挡在门外，代价与收益不成比例。

改为：**降级为 `causeFreeText`（自由文本本就不参与联动校验）+ 案件正常导入 + 在导入结果里逐行标出「案由已降级，请事后人工核对」+ 审计记录降级条数**。因此也不再需要在导入预览阶段做异步案由校验。

### 保全续封提醒：不建 Deadline 镜像行

**先纠正一处事实认定**：第五节原记「保全到期未进期限体系」，据此推论「ICS 日历订阅收不到保全提醒」——**该推论错误**。`queryScheduleItems` 已包含 `preservationProperty` 并映射为 `type: "deadline"`，而 ICS 路由正是走这个查询，所以**日程页与日历订阅一直是覆盖保全到期的**。

真正的缺口只有一处：**cron 提醒扫描查的是 `prisma.deadline` 实表，保全不在其中，因此站内通知与企微/钉钉推送完全不覆盖保全到期。** 且 `PreservationCase.remindDays`（默认 `[30,15,7,3,1]`）自 v0.44 起只写不读，是死配置。

**选择在扫描里直接覆盖源表，而不是建 Deadline 镜像行**，两条理由：

1. **提前量不同**。cron 的 `OFFSETS` 是 `-3/-1/0/+1`，对答辩、举证够用；续封要备材料、跑法院、等裁定，提前 3 天通知等于没通知。建 Deadline 行会让保全被迫接受这个提前量，反而不如现状；直接扫源表才能让各案自己的 `remindDays` 生效。
2. **避免双写不一致**。镜像行需要额外关联字段与同步逻辑，`expiryDate` 一改两处就可能不同步——正是第四节第 3 条批评过的模式。

实现：到期当天与逾期首日一律提醒（此时效力可能已消灭），其余按本案 `remindDays`；优先级 ≤3 天 URGENT、≤15 天 HIGH、其余 NORMAL；通知正文带查扣冻规定第二十七条的后果提示；按 `refType = PreservationExpiry:<天数>` 当日去重。已用临时数据实测 30/7/0 三档均触发、重复运行全部抑制，测试数据已清理。

**该项不涉及 schema 变更**，升级时无需额外迁移。

### 保全状态自动流转 —— 已实施（自动翻转 + 通知）

体检时发现 4 条财产条目中两条已逾期 49 天和 61 天、状态仍为 `ACTIVE`，系统无任何 `ACTIVE`/`RENEWED` → `EXPIRED` 的流转逻辑。

**判断依据**：按查扣冻规定第二十七条，期限届满未办延期手续的，效力「消灭」——这是法律上自动发生的事实，不依赖任何人的动作。因此数据库中仍标记为 `ACTIVE` **不是待处理状态，而是与法律事实不符的错误数据**。

进一步看两个方向的错误代价，严重不对称，据此选择朝安全方向失败：

| 数据错误方向 | 后果 |
|---|---|
| 显示生效中，实际已失效 | 律师不行动，被保全人转移财产。**不可逆** |
| 显示已过期，实际已续封（未录系统） | 律师看到告警去核对并更新记录。**自我修正** |

**实现**：只处理 `expiryDate` 早于今天零点的条目（到期当日仍在期限内）；翻转后发 URGENT 通知，正文写明「若实际已办理续封，请在系统中更新记录」；每条单独记 `PRESERVATION_STATUS_AUTO_EXPIRED` 审计。翻转天然幂等——状态变更后不再命中查询条件。

已在真实存量数据上实测：2 条逾期条目正确翻转，2 条未到期条目（含一条 `RENEWED`）不受影响，重复运行不再翻转、不重复通知。

### 程序删除确认文案 —— 已改为显示真实数量

原文案「该程序下的所有开庭、期限、备忘和材料记录将被一并删除」有两个问题：一是笼统，人对「所有相关记录」会习惯性点确定，对「3 条期限」会停手；二是不准确，`Document` 外键是 `SetNull`，材料本身不会删。

现改为按实际数量生成：「该程序下的 3 条期限、2 场开庭、5 个环节将被一并删除……（材料不会被删除，仅解除与本程序的关联。）」

**未采用软删方案**（推翻本节初稿建议）：数据库备份已 cron 化，误删可整库恢复，软删的边际价值仅是免于整库恢复；而软删要求每个查询都加 `deletedAt: null`，漏一处即显示已删数据，是持续渗漏的维护负担。真实风险不在「删了没法恢复」，而在「人会无视通用警告」——显示真实数量是最便宜的九成解。若日后真发生误删事故，再上软删不迟。

### 仍挂账（按优先级）

1. **TimelineEvent / AuditLog 手工双写**（第四节第 6 条），漏写无感知。中期在 service 层做统一记录入口。
2. **`deleteProcedure` 服务端无兜底断言**。客户端已有确认弹窗且现显示真实数量，暂不处理。
3. **`Deadline` / `Hearing` 硬删无恢复**。已评估暂不上软删，理由见上；出现实际误删事故后重新评估。
