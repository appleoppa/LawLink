# LawLink 业务端与管理后台分离方案

> 状态：第一阶段已实施；第二阶段按全新版本标准实施，Schema 修改与旧路由删除已获批准，数据库迁移执行仍待 SQL 审阅确认
> 确认日期：2026-09-06

## 一、目标

LawLink 保持单体应用、单库和统一登录，不建设另一套部署。界面与权限语义分为三个相互独立的维度：

1. 业务岗位决定案件、客户、材料、财务等业务访问；
2. 系统管理资格决定能否进入管理后台并配置组织、规则、接入和安全项目；
3. 审批资格继续按事项、案件类别、用章事项和印章类型独立授权。

同一自然人只保留一个日常账号，可以同时具有经办律师岗位、系统管理资格和特定审批资格。不得用两个日常账号拆分同一人的业务记录与管理审计。

## 二、第一阶段：管理空间分离

第一阶段不修改数据库 Schema、角色语义、审批资格或案件可见性，只调整信息架构和页面壳：

- 业务端保留现有主工作流；原“设置”更名为“个人设置”，只展示本人资料与登录安全；
- 新增 `/admin` 管理后台，使用独立导航、顶栏和持续可见的“系统管理模式”提示；
- 超级管理员从用户菜单进入管理后台；现有主任律师仍可进入其原有的提醒维护和批量导入页面，不扩大权限；
- 管理后台按“组织与人员—业务规则—系统接入—安全与审计”组织现有页面；
- 第一阶段复用现有设置页面及组件，不复制业务逻辑，不修改 Server Action；旧路由暂时保留为兼容入口；
- 管理后台在桌面与窄屏均提供明确的“返回业务系统”入口。

管理后台页面映射：

| 分组 | 页面 |
|---|---|
| 组织与人员 | 律所信息、用户管理、岗位角色、律师团队 |
| 业务规则 | 审批权限、归档制度、阶段模板、自定义字段 |
| 系统接入 | AI 与元典、快递接入、提醒维护、批量导入 |
| 安全与审计 | 审计日志 |

## 三、第二阶段：权限身份分离

第二阶段把当前 `ADMIN` 中混合的业务岗位与系统管理资格拆开。目标状态为：

- 叶森的业务岗位可登记为经办律师，同时另行持有系统超级管理员资格；
- 系统管理员不因管理资格自动取得全所案件正文、材料下载、业务写入或审批资格；
- 审批资格继续通过审批权限组授予；如需紧急排障访问业务数据，应采用有理由、有限时、完整审计的特别访问机制；
- 管理资格的授予、撤销、会话失效和至少一个有效超级管理员保护均写入审计。

第二阶段第一步新增独立系统身份枚举 `SystemRole`，取值为 `NONE`、`SUPER_ADMIN`，并在 `User` 增加非空字段 `systemRole`，默认值为 `NONE`。迁移时只把现有 `role = 'ADMIN'` 的账号补记为 `systemRole = 'SUPER_ADMIN'`，不在迁移中推测或改写其业务岗位。

Schema 修改和迁移 SQL 于 2026-09-06 获批准，数据库执行随后另行获批并完成。该批准不覆盖现有 `ADMIN` 业务权限撤销、叶森业务岗位改写或运行时鉴权切换。运行时仍须在后续改造中逐一把系统管理判断迁移到 `systemRole`，把业务访问判断保留在 `role` / 自定义岗位角色，并单独处理至少一名有效超级管理员保护、会话失效和审计。

2026-09-06 进一步确认按全新版本标准实施，不保留旧系统数据、角色或网址兼容逻辑。目标边界如下：

- `/admin/*` 是后台唯一入口；删除旧 `/settings/*` 后台路由及其兼容处理，只保留 `/settings/profile` 作为个人资料与登录安全入口；
- 会话每次按数据库当前值刷新 `systemRole`，所有系统配置、账号、岗位、团队、审批权限、接入密钥和后台审计操作改为校验 `SUPER_ADMIN`；页面隐藏不能代替 Server Action 和下载接口鉴权；
- 主任律师既有提醒维护和批量导入资格保留；`SUPER_ADMIN` 也可从后台进入这两项维护功能，但该系统身份不扩大案件正文、财务、附件、导出或审批资格；
- 用户管理分别展示业务岗位和系统管理身份。授予、撤销 `SUPER_ADMIN` 与停用账号均在事务内复核操作者及最后一名有效超级管理员，写入审计并提升目标账号 `sessionVersion`；不得修改自己的系统管理身份；
- `UserRole` 只保留 `CUSTOM`、`PRINCIPAL_LAWYER`、`LAWYER`、`ASSISTANT`、`FINANCE`，移除混合型 `ADMIN`；新系统初始化的超级管理员同时取得 `systemRole = SUPER_ADMIN` 和真实业务岗位，不再通过业务岗位推导管理资格；
- 管理后台页面和组件归入 `(admin)/admin`，个人资料组件留在 `(app)/settings/profile`；不保留从后台反向引用旧设置页面的实现。

移除 `UserRole.ADMIN` 的 Schema 修改及旧 `/settings/*` 后台路由文件删除已于 2026-09-06 获明确批准。数据库迁移 SQL 生成后仍须单独展示并获得执行确认；不得把生成 SQL 视为已经执行。

第一阶段已经执行的系统身份字段 SQL 为：

```sql
CREATE TYPE "SystemRole" AS ENUM ('NONE', 'SUPER_ADMIN');

ALTER TABLE "User"
ADD COLUMN "systemRole" "SystemRole" NOT NULL DEFAULT 'NONE';

UPDATE "User"
SET "systemRole" = 'SUPER_ADMIN'
WHERE "role" = 'ADMIN';
```

第二阶段已生成、尚待执行确认的 SQL 位于 `prisma/migrations/20260906220000_remove_admin_business_role/migration.sql`。该迁移把原混合型业务岗位规范为 `LAWYER`，清理印章配置数组中的退役枚举值，并重建不含 `ADMIN` 的 `UserRole`；全部语句置于同一事务中。

## 四、验收

- 普通业务导航不再混入系统配置；
- 个人设置不展示律所级、组织级、接入级或审计级配置；
- 管理后台入口、当前模式和返回业务系统路径明确；
- 非管理员不能借由新路由访问原本无权访问的页面；
- 主任律师仅保留原有提醒维护与批量导入权限；
- 通过 lint、typecheck、Prisma validate、build，并在 1440、1280、390 宽度检查 `/admin`、代表性管理页面和 `/settings/profile`。
