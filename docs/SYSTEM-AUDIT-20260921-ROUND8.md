## 一、本轮修复

### ① 搜索取数窗口早于权限过滤（同型第二例）

**位置**：`src/server/search/actions.ts`

`take: 40` 取全所最近文档 → 逐条 `canReadDocument` 过滤 → 截 `limit`。若最近 40 份文档都不属于本人，**本人自己案件里的材料会搜不到**，表现为「系统说没有」。律所越大、该律师办案占比越低，漏得越狠。

与第七轮 `listArchiveBorrows` 完全同构。按 AGENTS「第二例即全仓检索同形态」扫了全仓 9 处候选，**确认只有这两例**；其余都在数据库层用 `matterAssociationFilter` / `matterVisibilityFilter` 过滤，做法正确。两处例外同一根因：权限判定需逐条异步调用，无法下推为 `where`。

**修法**（非简单放大窗口）：复用现成的 `matterReadVisibilityFilter` / `intakeReadVisibilityFilter` 做**超集粗过滤**下推到 `where`（已覆盖 CUSTOM 角色与团队范围），精确判定仍由逐条 `canReadDocument` 负责，候选窗口提到 200。

**实证**（不靠推演）：在探针库插最小数据集（我的案件 d1 / 他人案件 d2 / 我上传的孤立文档 d3）实跑：

| 场景 | 结果 |
|---|---|
| 非 manager（带归属条件） | `[d1, d3]` —— 正确排除他人案件 d2 |
| manager（过滤器返回 `{}`） | `[d1, d2, d3]` —— 空对象确实匹配全部，不误排除 |

**过程中自己引入又修掉的 bug**：初版把 `visibilityScope` 平铺进 `where`，与关键词条件同名 `OR` 键互相覆盖，归属过滤会静默失效。已改为 `AND: [可见性, 关键词]` 包裹，并在注释里写明原因。

**已知取舍**：仅凭用印/审批通道可读、且既不挂案件也不挂收案、又非本人上传的孤立文档不进候选池。这类文档通常仍挂在某案件下，影响有限；彻底解法需把审批通道物化为可查询关联，另行排期。

### ② AI 外发台账的发起人恒为空

**位置**：`src/lib/ai/client.ts` 及全部 14 个调用点

`ExternalCallLog` 有 `userId` 列，但 `aiChat` / `aiVision` 从不填充 → 台账只能回答「系统某时刻调了一次 ai-chat、耗时多少」，答不了「谁发的」。律所需要能对客户说清材料由谁外发。

**修法**：`aiChat` / `aiVision` 增加可选 `userId` 并透传至 `withExternalCallLog`；**14 个调用点全部补齐**（脚本核验 14/14，无遗漏）。其中：

- 9 处有 session 的 server action：直接传 `session.user.id`（其中 6 处原本 `await requireSession(...)` 不接返回值，一并改为接收）；
- 后台链路 3 处：`sms/analysis` 从 `SmsMessage.receivedById`（粘贴短信的律师）取，透传至 `analyzeDocumentText` 与 `recognizeText`；`sms-parser-ai` 从调用方 session 取，**并补上原本缺失的 `logAction`**（此前连动作名都没有）。

### ③ 收案阶段材料的 AI 审查不留痕

**位置**：`src/server/ai/review-document.ts`

`ReviewRecord.matterId` 必填带外键，故原实现是 `if (reviewMatterId)` 才写记录——收案阶段（`intakeId`）的材料送 AI 审查**没有任何追溯**，而收案恰是客户身份证、合同草稿最集中的时候。

**修法**：不改 Schema（避开迁移审批），外发留痕改走 `AuditLog`（AGENTS §八：不可由业务代码删除）。两条路径并存——`ReviewRecord` 是业务记录（案件内回看），`AuditLog` 是合规留痕（答「谁把哪份材料发给了外部模型」），detail 含 matterId / intakeId / 文件名 / 外发字符数 / 是否截断 / 条目数。

新增的 `AI_REVIEW_DOCUMENT` 动作**被第七轮那个元测试自动验证可读**——这正是元测试的价值。

### ④ README 的安全声明已过期

`npm audit --omit=dev` 报 **2 项 high**（`nodemailer ≤9.1.0`，共 10 条 CVE），而 README 写着「当日全量及生产依赖审计均为 0 个已知漏洞」。

**可利用性评估**（不夸大）：项目用 Credentials Provider，不启用 NextAuth 邮件登录（`next-auth` 的 `email.js` 才 `require("nodemailer")`，按需加载，本项目不触发）；自身用法为固定配置的 `createTransport` + `sendMail`，收件地址取自管理员录入的用户表。**多数 CVE 在本项目用法下不可直接触发**。真正的问题是文档在对部署方做一个已不成立的承诺。

**修法**：升级 `nodemailer@10.0.10`（用法极简，兼容）；`package.json` 的 `overrides` 固定版本——否则 `next-auth@4` 的 `^7.0.7` peer 约束会让部署方 `npm ci` 失败（该文件本就在用 overrides 机制，做法一致）。README 与 SECURITY.md 改为带核对日期、明示「不随时间自动成立」的表述，并记录本次评估过程。

升级后 `npm audit` 全量与生产均为 0，测试 / typecheck / build 全通过。

### ⑤ 提示词注入：输出上限（新镜头）

**已确认关闭的通道**（设计质量高，值得记录）：文书正文是不可信输入，但字段写入面有**双重白名单**——生成侧只认 `caseNumber` / `courtName`（`analysis.ts`），应用侧再校验 `["caseNumber","handlingAgency"]`（`confirm-actions.ts`），另有前置值复核（建议生成后原值被改过即拒绝）、归属校验、律师逐条确认。模型无法指定要改哪个业务字段。

**本轮补上的**：`normalizeAnalyzed` 此前对数组数量与字符串长度无约束——一份文书可产出任意多条建议淹没律师的确认界面，超长字符串原样进库。已加 `MAX_FIELDS=30` / `MAX_EVENTS=20` / `MAX_CASE_NUMBERS=20` / 文本 200 字 / note 500 字。

**新增 5 例注入回归测试**：海量输出被截断、超长文本被截断、非法 `kind` 归一到白名单、被诱导输出自然语言时**拒绝而非猜测**、残缺 JSON 同样拒绝。

写测试过程中的一次自我纠正：我最初断言「非 JSON 时应安全归空」，实跑发现会抛错。查上层确认 `analyzeInboundFile` 有 catch 并落 `analysisState=FAILED` + `analysisError`，律师在收件箱看到失败并可手动重跑——**抛错是有意的降级设计，不是缺陷**，是我的测试期望写错了，已改为断言拒绝行为。

### 首轮 `/archive` 500 的根因与价值

报错 `expireOverdue: Cannot read properties of undefined (reading 'updateMany')`——`prisma.archiveBorrowRequest` 为 undefined。

根因是本轮升级 nodemailer 时执行的 `npm install` 重装了 `@prisma/client`，覆盖了 `prisma generate` 的产物；`npx prisma generate` + 重启 dev 后全部页面恢复 200。**不是代码缺陷**，是我的操作顺序问题。

但它暴露了一件值得记录的事：**「769 测试全绿 + lint/typecheck/build 干净」与「全站 500」可以同时成立**。单元测试 mock 了 Prisma，构建不校验运行时 client 产物，只有真正打开页面才会发现。这正是 AGENTS §七要求走金线的理由，而前七轮都跳过了这一步。

（已核对：README 本地安装步骤第 59-60 行写了 `npm ci` + `npm run prisma:generate`，Dockerfile builder 阶段亦有 `npx prisma generate`，文档侧覆盖到位，无需加 postinstall。）

## 五、仍未覆盖（如实声明）

- **金线走查的深度**：做到了「登录 + 页面可达 + 交互点击 + 关键改动的界面核对」。**仍未做**写操作闭环——新建收案→冲突检索→转正式案件→登记期限→确认→结案→归档的完整点击，以及借阅申请→审批→归还。原因是这些会在库中产生业务数据；如需覆盖，建议在独立演练库执行。UI 呈现与 v4 墨案效果图的逐页比对也未做。
- **多用户并发事务实测**（Serializable 重试、advisory lock 竞争）。
- **提示词注入的社工面**：注入可让建议卡片上的 `title` / `note` 显示误导文本（如「此开庭已取消」）。缓解手段是律师对照原文核对，但**原文回看未实现**（`SmsSuggestion.sourcePage` / `sourceExcerpt` 字段已预留，逐页渲染是 B2 后续项）。这是当前注入面**唯一实质剩余风险**。
- **OCR 可信度边界**：识别错一个日期就是错一个期限。
- 短信取件的平台兼容性（无真实样本）、`src/components/` UI 一致性、性能与 N+1。

## 六、一个判断

这个系统的**代码正确性与安全底子确实扎实**——本轮专打安全面，六片全干净，提示词注入的关键通道也早已用双重白名单关死。

但新发现的问题继续呈现同一个模式：**能力做了，配套的可追溯性 / 可用性没跟上**。搜索有权限但搜不全、AI 有管控但台账记不住是谁、审查有记录但收案阶段漏掉、依赖修过但声明不更新。这和第六轮「提醒发得出去但不知道有没有到」、第七轮「审计记了但读不出是什么操作」是同一路。

**建议把这条当作下一轮的固定镜头**：对每个已交付能力问三句——谁做的能查到吗？做了什么能读懂吗？没做成会有人知道吗？
