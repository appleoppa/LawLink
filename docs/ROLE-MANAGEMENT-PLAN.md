# 用户角色管理改造方案

日期：2026-09-06

状态：叶森已确认方案、Schema 修改及本地迁移执行；数据库角色结构与行政配置已启用。真实数据库回滚验收、管理员浏览器配置保存及用户表单角色选项验收通过；覆盖范围见 `docs/ROLE-MANAGEMENT-MIGRATION.md`。

## 1. 目标与当前问题

在「设置 → 角色管理」新增、编辑、停用自定义角色，并在用户管理中直接分配。预置「行政」，后续新增「实习人员」「档案管理员」等无需改代码。

当前 User.role、用户表单和服务端校验均固定五个角色。权限判断分布于案件、客户、财务、公告、律所资料、导出、设置和审批服务。仅增加角色名称无法实现可配置权限，甚至可能被旧分支错误授予权限。

## 2. 用户操作

1. 仅超级管理员看到「角色管理」；用户管理提供「管理角色」入口。
2. 角色列表展示名称、类型（系统内置/自定义）、说明、启用状态、使用人数和权限摘要。
3. 新建角色填写名称和说明，按业务功能勾选权限及数据范围；默认不勾选业务权限。名称去除首尾空白后不得重复，不得冒用系统角色名称。
4. 六个内置角色（原五种及行政）允许管理员修改显示名称和介绍，权限固定，不可停用或删除；支持从普通内置角色复制一份可编辑的自定义角色，超级管理员不可复制。改名不改变系统身份或任何业务授权。
5. 「行政」按既有固定记录标识纳入内置角色，沿用其现有权限与用户关联，不重建记录。创建用户或调整角色时直接选「行政」或管理员更改后的名称。每人一个岗位角色，可另加入多个审批权限组。
6. 保存角色前展示影响账号数量和权限增减；用户角色变更显示新旧角色。版本冲突要求刷新，不能覆盖他人刚保存的配置。
7. 角色不提供删除。停用后禁止新分配，已分配账号暂停业务访问并提示联系管理员调整角色；保留账号及历史记录。重新启用后恢复访问。

## 3. 功能与数据范围

角色配置采用固定、受代码校验的权限项目，不允许管理员输入任意权限字符串；本次提供功能级配置，不建设字段级权限矩阵。

| 功能组 | 可配置项目 | 范围及边界 |
| --- | --- | --- |
| 案件与收案 | 查看、收案登记、案件办理 | 查看选择本人经办/按已有团队授权/全所；编辑仍须满足案件经办身份、程序和状态要求 |
| 客户 | 查看、维护 | 与本人经办案件相关/全所；维护与查看分别授权，联系人敏感信息沿用脱敏规则 |
| 案件材料 | 查看目录、上传、下载 | 受案件访问范围约束；团队只读授权不自动开放上传下载 |
| 日程与记录 | 查看、维护 | 本人及可访问案件；团队只读不能授权改写他人的记录 |
| 财务 | 查看、收付款维护、开票执行 | 本人经办/全所独立设置；财务范围不等于案件正文范围；开票执行仍检查已批准状态 |
| 归档与导出 | 查看归档、提交归档、案件导出、报表查看/导出 | 办理遵守案件经办及状态限制；导出独立授权，团队只读不能用于导出；提交归档不授予审批权 |
| 行政事务 | 公告管理、律所资料管理、快递登记及维护、外部联系人维护及审核 | 按现有对象范围和归属检查；快递管理可单独授予全所范围 |
| 用章申请 | 发起用章申请 | 案件事项仍校验关联资格；非案件事项按已启用事项规则校验 |

始终开放个人资料维护、本人通知和个人工作入口。工作台、全局搜索、统计摘要、附件直链、下载接口、日历订阅及后台推送也必须应用相同权限范围；无权限功能不应通过聚合数据泄露。

系统管理能力（用户/角色/审批授权管理、团队配置、系统接入密钥、系统设置）继续仅限超级管理员，不作为普通自定义角色可勾选项。既有内置主办律师的管理能力保持兼容。

审批工作台继续依申请人、处理人、审批权限组和超级管理员规则判断。不能因为普通角色未勾选案件模块就阻断独立获授的申请级审批访问，也不能因此开放整个案件。角色停用或账号停用时停止业务访问及成为当前有效审批人的资格；恢复后按当时的有效授权重新判断。

## 4. 「行政」初始权限

- 开放个人资料、本人通知和个人日程。
- 允许管理公告、律所公共资料、本人快递登记及维护、外部联系人录入维护，以及发起已配置的非案件用章申请。
- 不预授全所案件、客户库、财务、案件材料下载、报表导出、外部联系人审核或系统配置权限；管理员可按实际职责调整可配置项目。
- 审批与盖章回填不预授，管理员在既有审批权限组中选择具体人员、事项、案件类别和印章类型。
- 角色名称不代表执业资格，不自动加入律师团队或设为案件主办。

## 5. 数据设计与兼容

拟新增 RoleDefinition 和 RolePermission 两张表，User 增加可空 roleDefinitionId 关联；UserRole 增加 CUSTOM 值供自定义角色使用。现有五个枚举值及历史账号角色保持原值，内置角色通过代码中的集中权限目录展示。

- RoleDefinition：id、唯一规范化名称、说明、active、version、创建/更新时间及权限/用户关联。
- RolePermission：角色关联、受白名单校验的 permissionKey、scope，角色与权限键唯一；外键限制物理删除。
- User：原 role 为 CUSTOM 时必须关联有效自定义角色；原五类角色不允许同时关联自定义角色。服务端和数据库约束共同保证一致性。
- 新建角色、角色调整、停用/启用、账号改角色及审计同事务执行；沿用现有权限事务锁，更新账号 sessionVersion 撤销旧会话。
- 保存角色时检查当前操作者仍为有效超级管理员，事务内重新核验权限与版本；保留不能改自己角色和至少一个有效超级管理员的限制。
- 旧角色对应原有行为；CUSTOM 只能走新权限解析，不得落入旧默认助理分支或拥有旧角色隐式权限。无效关联和未知权限默认拒绝。
- 每次受保护请求加载当前有效角色与权限；敏感写入在事务内复核，角色停用或权限撤销后旧页面不能继续操作。
- 历史审批人、案件经办人、审计操作者仍用 User.id；角色改名不修改历史记录。新的角色审计记录变更前后名称、权限及范围，不记录个人证件、电话或密码。

迁移只增加本次表、关联字段、约束、索引、CUSTOM 枚举及预置行政配置；不批量替换现有账号角色、不重置数据库、不混入其他未执行迁移。生成前核对工作区及实际迁移状态。确认方案后先生成 SQL（优先 create-only；若环境不支持，使用明确的前后 Schema diff 仅生成 SQL），展示具体内容和影响，再申请执行本地迁移。

## 6. 实施范围与顺序

1. 确认本方案及 Schema 修改授权；先更新 AGENTS.md、PRD、DATA-MODEL 与 UI-DESIGN，规定下列新增目录用途。
2. 数据模型及迁移 SQL → 类型与权限目录 → 权限解析、查询范围及断言 → 角色与用户服务 → 界面。
3. src/lib/roles/ 维护固定权限目录、范围规则和角色解析；src/server/roles/ 维护校验、事务和管理操作；设置页面就近位于 src/app/(app)/settings/roles/_components/。文件使用英文短横线命名。
4. 审计 src/lib/permissions/、鉴权会话、审批有效人员查询、各 Server Action、API、页面和导航中的直接角色判断，分别接入功能与对象范围检查。保留仅限系统管理员的检查，不做机械全局替换。
5. 联动用户创建/角色编辑、用户列表、个人资料角色展示和同事选择列表；自定义名称统一显示，承办人员选择不能凭岗位名称推断律师资格。
6. 迁移执行获确认后验证本地数据库及浏览器完整流程，保持既有未提交改动，不进行发布或推送。

## 7. 验收标准

- 新建自定义角色 → 选择权限范围 → 创建或分配用户 → 新身份访问；「行政」在用户角色列表中直接可选。
- 角色改名、停用、重新启用、重复名称、并发编辑均有明确反馈；停用账号和停用角色均不能继续访问业务或接收可处理的新审批。
- 无权限用户直接调用页面、Server Action、API、下载和导出链接均被拒绝；验证读权限不能变成写权限、全所财务不能变成全所案件正文权限。
- 切换角色、撤权、旧会话、仅团队只读、仅申请级审批、历史处理人查阅及 CUSTOM 无效关联均有有效的权限测试。
- 回归原有五种角色、超级管理员保护、团队边界、审批/盖章回填、附件与敏感资料脱敏；既有账号权限不因迁移改变。
- 主动运行 lint、typecheck、prisma:validate、build 及相关权限测试；核对 3000 端口归属本仓库并打开站点。浏览器验证管理员配置和非管理员实际权限，登录页可访问不替代业务验收。

## 9. 内置角色显示资料调整（后续明确要求）

用户要求“行政改为内置角色，另外内置角色的名称和介绍也要能修改”。本次复用现有存储完成：原五类角色在 SystemSetting 保存独立的显示名称、介绍和版本；行政保留固定 RoleDefinition 标识及当前权限，只开放名称和介绍。内部枚举、用户关联、权限配置不变，无 Schema 修改或数据迁移。目录沿用 src/lib/roles、src/server/roles 及原有页面。

所有角色的当前名称统一判重，内置默认名称与固定标识保留给对应系统角色，防止冒用。管理员显示资料保存与审计同事务、并发版本冲突明确提示；不因改名使用户退出登录。角色管理、用户分配选项、本人资料及相关人员列表同步显示新名称。测试覆盖固定标识保护、名称冲突、并发修改、权限不变及界面交互。

本次实现与验证完成：53 个测试文件、442 项测试通过；lint、typecheck、Prisma validate 和生产构建通过。浏览器确认六个内置角色都有编辑资料入口、行政不再显示自定义权限编辑；行政资料保存成功。临时修改管理员名称和介绍后，角色列表、个人资料及用户管理同步回显，登录有效；验收后已恢复原名称和介绍。没有改变既有用户角色、权限或会话版本，没有执行数据库结构变更或迁移。
