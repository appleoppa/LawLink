## 一、范围与非目标

本文覆盖三件事：

1. 五对象目标模型的概念责任与两步迁移路径（样例验证通过为前提）；
2. 三项制度级权限决策的决策材料与选项（第八章遗留）；
3. 两条纵向样例的具体设计（含故障注入点），作为"复用 vs 重建"的判定工具。

## 二、五对象目标模型

### 2.1 概念责任

| 对象 | 回答的问题 | 关键属性 | 不放什么 |
|---|---|---|---|
| 主体 Party | 这个人/机构是谁 | 归一身份（证件类型+规范化号码）、名称（含曾用名/更名记录）、类型 | 案件角色、开票信息 |
| 委托 Engagement | 为何服务、为谁、到何处 | 委托人、服务范围（文本+结构化条目）、有效期、终止状态、收费安排引用 | 程序进展、任务 |
| 工作事项 Matter | 正在解决什么/交付什么 | 现有 Matter 字段收敛后保留；成为权限与日常组织默认单元 | 委托范围字段、程序专属字段 |
| 程序 Procedure | 在哪个机构、哪个阶段、以什么角色 | 现有 MatterProcedure 基本不变 | 承办范围（下沉到事项×程序关系） |
| 材料版本 MaterialVersion | 哪个版本的什么材料 | 不可覆盖版本链、页级文本层、来源（原件/扫描/回传）、处理状态 | 业务判断 |

关系骨架（增量最小化）：

```
Party 1─n Engagement（委托人）
Engagement n─m Matter（EngagementMatter 关联，含适用范围版本）
Matter 1─n MatterProcedure（现状保留）
Matter n─m Procedure（共享程序场景，先不建，见 2.3）
Document → 升级为 MaterialVersion 树（familyId 真正启用）
```

### 2.2 两步迁移路径（样例验证通过后）

**第一步（低风险）**：新增 `Engagement` 模型与 `EngagementMatter` 关联；现有 `Billing` 增加可选 `engagementId`；页面语义不变，收案表单同步创建默认委托（范围=收案申请快照）。此步只加不减，回退容易。

**第二步（在第一步数据积累后）**：把 Matter 上属于委托的字段（服务范围、顾问期限类字段）逐步搬出；`MatterLink` 增加关系类型枚举（发回重审/衍生执行/关联合同/仅供参考）、方向与时间；Matter 重定义为工作事项。

### 2.3 程序共享：先观察后决策

`MatterProcedure` 是否升级为跨事项共享实体，取决于"多委托同程序"真实样本量。默认不共享：不同委托对同一法院程序各建程序记录，用 MatterLink（关系类型=同案号）关联。触发共享建设的条件：同一法院案号在系统内出现 ≥3 个独立程序记录且材料重复上传成为负担。

## 三、九个验收样例（模型成立的判定标准）

| # | 样例 | 现有模型的表达障碍 | 目标模型的表达方式 |
|---|---|---|---|
| 1 | 一委托多事项 | 无委托实体，收费安排只能挂单案件 | Engagement 关联多个 Matter |
| 2 | 一事项多程序但只承办一段 | engagement 只有 ENGAGED/INFORMATIONAL 两值 | EngagementMatter 范围条目化 |
| 3 | 程序发回重审后事实与角色变化 | MatterLink 无类型；发回只能新建全案 | 程序内阶段重置 + Link(type=发回) |
| 4 | 同主体分别是客户与对方 | Party 已归一（现状可表达） | 验证现状，不要求改 |
| 5 | 委托终止但款项未结 | 无委托终止态；Billing 无生命周期 | Engagement.terminatedAt + 核销留余额 |
| 6 | 程序结束但服务未完成 | Matter.status 单值强绑定 | 状态轴分离（程序轴≠服务轴） |
| 7 | 一事项先后涉及多份委托（范围与收费不同） | Billing 替代委托语义，无法表达先后 | EngagementMatter 带生效区间 |
| 8 | 同一程序被多事项引用、各自可见材料不同 | 程序直属于单 Matter | 共享程序 + 事项×程序可见性（2.3 触发后） |
| 9 | 主体更名后历史提交包保持原貌 | Party 快照机制已有（conflict 侧） | 全面化：审批、归档、提交包均用快照 |

样例 4 现状已可表达——验收清单不是全盘重建的理由，逐项判定。

## 四、三项制度级权限决策（决策材料）

> **决策记录（2026-09-13，叶森批准）**：4.1 采用选项 A（受限标记，已实施：`Matter.teamAccessRestricted` + `teamMatterFilter` 过滤）；4.2 维持现行默认，三分离原则记入 AGENTS.md；4.3 方向批准（自确认清单），接线因触及"禁止绕过审批"红线后置到审批模块专项。详见 AGENTS.md"P0 底线补强批次决策"。

### 4.1 团队历史访问默认

- 现状：团队负责人自动可见成员原始立案/当前主办的全部案件（实时计算）。
- 重评关切：人员调组时历史案件进入访问范围；越权阅读面大。
- 选项 A（维持+补丁）：现状不变，Matter 增加 `teamAccessRestricted` 标记（受限事项不进团队汇总），撤权后存量访问进复核提示。成本：一个字段+过滤条件。
- 选项 B（转明确授权）：团队仅作分配工具，案件访问一律显式授权。成本：存量补授权脚本+日常操作增加。
- 决策依据建议：统计现有团队汇总的实际点击/查看频率（审计日志可得）。若低频，说明默认开放价值有限，倾向 B；若高频，倾向 A。

### 4.2 建号必传证件照片

- 决策要点（报告 v5 定稿口径）：账号实名、身份核验、证件照片留存是三件事，按核验目的决定。
- 选项 A（维持现状）：所有账号实名+证件照。
- 选项 B（目的分层）：内部正式人员按人事需要决定是否留存照片（可只登记证件类型+号码不留照）；外部协作账号（如出现）不采集证件，用内部 ID+审计关联。
- 注意：选项 B 触及 AGENTS.md 个人身份章节已确认内容，须先改制度再实施。

### 4.3 低影响动作自确认

- 选项 A：维持全部按事项审批。
- 选项 B：管理后台增加"自确认清单"配置（如：非法定代表人章、无附件文书修订），命中清单的动作由申请人自我确认+审计，不走审批流；法定代表人章、归档、开票维持审批。
- 实现成本：一个配置项 + 审批提交入口的分支。

## 五、两条纵向样例（复用/重建判定）

### 样例 A：材料 → 证据项 → 提交包 → 材料变更

流程：收案上传一份多页扫描合同 → OCR 文本层落库（带页码） → 律师标注证据项（引用页段） → 生成证据目录（固定版本） → 原材料被替换新版本 → 旧提交包不变且被标记"来源已更新，请复核"。

验收点：
1. 提交包固定的材料清单引用的是版本号而非"最新"指针；
2. 版本替换后提交包内容字节不变（校验值验证）；
3. 系统标出受影响成果并要求复核，不静默更新；
4. 权限：证据项、OCR 文本、提交包全程继承源文档授权；撤销协办授权后，以上全部不可见、检索不可命中。

### 样例 B：期限触发 → 确认 → 提醒 → 宕机恢复

流程：录入"判决书送达"事件 → 系统按规则版本计算上诉期并生成**待确认**期限 → 律师确认（起算事实、规则、结果留痕） → 提醒进入队列 → 模拟：发送时 webhook 超时（结果未知）→ 系统不盲目重发，标记待查 → 手动补发成功 → 全程留痕。

验收点：
1. 规则更新后重算只生成待复核结果，不覆盖已确认期限；
2. 投递三态（成功/失败/未知）区分处理；
3. 进程重启后队列可接续（模拟：扫描中途 kill，重启后补偿）；
4. 升级通知前校验接收人资格（无资格时进异常处理而非发送）。

### 判定规则

两条样例若能在现有代码中隔离出领域核心并通过 → 复用+替换模块；若必须维持双套事实或遍历修补 → 新建目标核心（范围按需扩大）。判定结论写入本文件的"判定记录"节后生效。
