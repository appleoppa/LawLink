# LawLink UI v4 现状审计

> 状态：审计结论，不是当前执行规范
> 审计日期：2026-08-15
> 当前有效规范仍为：`docs/UI-DESIGN.md` v3.3

## 一、结论

LawLink 不缺少页面，也不缺少视觉尝试。当前主要问题是：**v3.3 设计稿、全局 CSS、shadcn 原子组件和各业务页面之间没有形成同一套可执行的 UI 架构**。

因此，v4 不应继续逐页“换皮”，也不应让网站生成工具重写主仓库。正确路径是先建立页面母版和组件边界，再迁移四类代表性界面，最后按业务金线扩展。

## 二、审计范围与边界

本次检查了：

- 当前设计规范 `docs/UI-DESIGN.md` 与 `docs/mockup/v3/` 八个原型；
- `src/app/globals.css`、AppShell、侧栏、顶栏和主要 shadcn 组件；
- 工作台、案件列表、案件详情、收案登记等核心实现；
- 本地运行界面的登录页、工作台、案件列表、案件详情和收案登记；
- 1280×720 桌面窗口下的真实数据与交互状态。

本次没有执行移动端浏览器实测；响应式验收列入 v4 实施门槛。

## 三、优先级结论

### P0：实施前必须解决

#### 1. 原子组件规则与现状冲突

`AGENTS.md` 规定 `src/components/ui/` 只放 shadcn CLI 生成的原子组件且不直接修改，但当前 `Button`、`Input`、`Select`、`Badge`、`Dialog`、`Sheet` 等已经承载大量 LawLink 定制样式。

这不是单纯的代码洁癖问题。它导致：

- 更新 shadcn 时难以判断哪些样式可以覆盖；
- 页面为了纠正原子组件默认值，继续叠加局部 class；
- 同一控件在不同页面出现不同圆角、间距和聚焦状态。

建议在代码阶段开始前先修改 `AGENTS.md`：新增 `src/components/patterns/`，用于 LawLink 品牌化组合组件；`src/components/ui/` 回归原子组件职责。

#### 2. 两套视觉语言仍然共存

v3.3 已确定浅色 teal 系统，但代码中仍能看到 v0.2 的蓝色、青色、暗色弹窗遮罩和其他历史样式。

静态统计显示：

- 23 个文件包含 150 处 Tailwind 硬编码十六进制颜色；
- 32 个文件包含 67 处内联样式；
- `Dialog`、`Sheet` 仍使用 `bg-black/80` 遮罩；
- `Button` 默认全圆角，而输入框默认小圆角，卡片又保留 shadcn 的大内边距。

动态颜色并非全部错误，但状态色、品牌色和数据可视化色必须分别进入语义 token，不能继续由页面自行决定。

#### 3. 复杂页面已经超过安全重构尺度

以下组件同时承担数据编排、状态、表单、布局和视觉细节：

- `procedure-workflow-panel.tsx`：2269 行；
- `intake-sheet.tsx`：1591 行；
- `procedure-content.tsx`：1478 行；
- `procedure-info-panel.tsx`：1330 行；
- `team-editor-dialog.tsx`：1282 行；
- `matter-detail-tabs.tsx`：1100 行。

在这些文件上直接做大面积视觉修改，极易影响权限、状态机和程序材料。v4 必须先抽取纯展示 pattern，再逐段替换，不能整页重写。

### P1：首批页面必须处理

#### 4. 缺少明确的页面母版

目前已有共享 AppShell，但页面内部仍各自实现标题、筛选、状态、指标、侧栏和分段导航。`ll-*` 类只能覆盖局部外观，不能约束信息架构。

v4 至少需要四种母版：

1. 工作台：任务与风险优先的指挥台；
2. 列表页：标题、查询、筛选、批量操作、数据区、分页；
3. 案件详情：案件上下文、程序切换、环节工作区、辅助侧栏；
4. 事务表单：高密度录入、渐进展开、固定提交区、错误汇总。

#### 5. 字号过度压缩

代码中约有 16 处 9/9.5px、263 处 10/10.5px、367 处 11/11.5px 文本。少量 10px 辅助标签可以接受，但当前使用规模已经影响中文可读性，尤其是在案件详情侧栏、环节导航和复杂表格中。

v4 建议把业务正文基线提高到 13px，次要信息不低于 11.5px；9—10px 只保留给极少量非关键标识。

#### 6. 色彩承担了过多无关含义

案件列表的日期使用 teal，容易被理解为链接；案件行同时使用红点、类别字标、状态徽章，多种信号相互竞争。图表又引入独立的多色体系。

v4 应固定：

- teal：主要操作、当前选择、可交互焦点；
- 红/橙：风险、逾期、阻断；
- 绿：已完成或已结案；
- 蓝/紫等：只在确有业务分类意义时使用；
- 普通日期、案号、金额不得仅因“需要强调”而上品牌色。

## 四、代表页面检查

### 1. 登录页

优点：左右结构稳定、表单焦点清楚、品牌与登录区分离。

问题：左侧营销文案占比偏高，品牌识别仍接近通用后台；登录表单区域缺乏部署实例或律所身份信息。该页不是首批重构重点。

### 2. 工作台

优点：问候、今日焦点、KPI 和图表已经形成清楚的三层结构，真实数据聚合完整。

问题：

- “办理中案件”等 KPI 同时出现胶囊数字和大数字，信息重复；
- 今日焦点为空时仍占据较大首屏面积；
- 图表区域更像统计报表，未直接回答“今天先处理什么”；
- 多色环图与系统语义色没有建立关系。

v4 工作台应把期限、开庭、待审批、待补正放在首屏行动区，经营指标降为次级概览。

### 3. 案件列表

优点：筛选完整、URL 状态明确、导出和分页均保留，业务信息密度符合律师使用场景。

问题：

- 标题、分段导航、搜索、筛选分成四层横向条带，视觉路径过长；
- 案件行同时出现状态点、类别字标、状态文本，信号重复；
- teal 日期看起来像可点击链接；
- 案件名称、客户和案号在 1280 宽度下截断较多；
- 表格实现是列表链接结构，后续做排序、列设置和批量选择时扩展成本高。

v4 建议把搜索、筛选、排序收敛为一个 `ListToolbar`，并重新定义列优先级。

### 4. 案件详情

优点：案件状态、期限、程序、环节、团队、重要事项、审批和财务已经在一个工作区内串联，业务覆盖完整。

问题最集中：

- 主区内部同时存在环节左栏、内容区和右侧业务栏，叠加全局侧栏后形成四层横向分割；
- 顶部摘要与“信息总览”重复展示客户、案由、案号、收案时间等信息；
- 信息总览因列宽不足出现“案／由”“相／对／方”等中文标签被拆行；
- 环节导航中的数量、状态和剩余天数被压缩到难以辨识；
- 右侧团队、重要事项、审批和财务纵向堆叠，首屏无法明确当前任务；
- 当前 1100—2269 行的大组件让任何版式调整都可能触碰业务行为。

v4 应将详情页定义为 `MatterWorkspace`，采用“固定案件上下文 + 可切换程序 + 单一主任务区 + 可折叠辅助栏”，并删除重复摘要。

### 5. 收案登记

优点：真实字段完整，固定提交区明确，表单密度高，能够覆盖复杂收案而不是只做演示表单。

问题：

- 基本信息一次出现过多同权重字段，用户难以判断先后顺序；
- 日期控件显示为美式 `MM/DD/YYYY`，与中文法律工作习惯不一致；
- 当事人表格式录入在较窄窗口下容易误填身份信息；
- “案件从这里开始它的生命周期”等文案偏产品宣传，不够实务化；
- 低频字段虽然存在“更多”，但整张表单仍缺少顶部错误汇总和完成度反馈；
- 关闭按钮的无障碍文本仍为英文 `Close`。

v4 不应删减字段。建议保留单一连续表单，按“基本信息—当事人—费用—附件与提交”建立锚点导航，对低频字段渐进展开。

## 五、v4 的验收基线

任何页面只有同时满足以下条件，才能算迁移完成：

- 页面使用已经定义的母版或 pattern，不在页面重新发明同类控件；
- 状态色、品牌色和图表色均来自语义 token；
- 不修改权限、Server Action、状态机和数据模型；
- 1440、1280、390 三个宽度无横向溢出，主要操作可见；
- 中文正文和关键状态在默认缩放下可读；
- 空状态、加载、错误、权限不足和长文本至少各检查一个代表场景；
- 走通“登录—工作台—新建收案—冲突检索—转正式案件—案件跟进—财务—归档”金线；
- 通过 lint、typecheck、Prisma 校验和生产构建；
- 本地 3000 端口确属 LawLink，并完成真实浏览器检查。
