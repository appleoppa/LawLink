# LawLink v1.3 使用与升级说明

适用版本：v1.3.0 / v1.3.1 / v1.3.2 / **v1.4.0**；核对日期：2026-09-21。v1.3.1 是公开说明与 CI 的维护版，业务功能与 v1.3.0 相同；v1.4.0 的升级须先做迁移基线标记，见本文「从 v1.3.x 升级：迁移基线重建」一节。

## 这一版改变了什么

管理后台从个人设置分离到 `/admin`，岗位角色、系统管理和事项审批分别配置。新增常设律师团队、自定义岗位、统一审批工作台、归档材料审阅以及个人身份资料管理。业务端保留案件、客户、财务、日程、审批、归档等日常入口。

| 事项 | 当前规则 |
|---|---|
| 系统管理 | `SUPER_ADMIN` 管理律所配置、账号、岗位、团队、审批授权与审计；不因此获得案件或审批捷径 |
| 业务岗位 | 每人一个岗位；内置岗位可改显示资料，自定义岗位按功能和数据范围授权，停用会影响所属账号访问 |
| 常设团队 | 负责人及获授查看范围的成员可只读查看当前团队成员原始立案或当前主办的案件，含历史案件；协办关系不向整个团队传播 |
| 案件经办 | 主办、协办、助理与常设团队分开；编辑、财务、附件及导出继续分别校验 |
| 事项审批 | 按操作、案件类别、用章事项及印章类型匹配；无合格审批人时阻止提交，超级管理员也需事项授权 |
| 审批历史 | 申请人、实际处理人等按申请范围查阅；批准不等于完成开票或盖章，不能再次驳回已批准事项 |
| 归档 | 送审时固定制度版本和材料快照；缺项、不适用须说明，批准导出核对固定材料及内容校验值 |
| 身份资料 | 人员证件资料与照片独立受控；照片加密，自动识别须人工核对，外部识别须确认接收服务 |

团队访问随当前有效成员关系、账号和授权变化。不要把团队负责人理解为全所管理员，也不要以审批附件查阅权推导对整案材料的访问权。

## 首次登录后的配置顺序

1. 在“个人设置 → 个人资料”核对本人邮箱和密码。首次 seed 生成的账号是“系统超级管理员 + 经办律师”；它尚未自动拥有所有业务或审批权限。
2. 进入“管理后台 → 律所信息”，补齐本所资料及法定代表人信息，按本所实际管理制度选择业务开关。
3. 在“岗位角色、用户管理、律师团队”设置实际岗位、独立账号与团队。新增账号需登记证件并上传证件照片；历史未补录账号仍可用，不能为了测试随意编造真实身份。
4. 在“审批权限”配置有效审批人、具体操作和事项范围，核对用章事项与印章适配。多人团队默认不得自批；单人执业确需自批时显式开启例外，法定代表人章仍核对身份。
5. 在“归档制度”配置本所采用的制度名称、版本、生效日期、原文和材料清单。系统参考清单不能自动视为本所制度。
6. 按需配置“AI 与元典”“提醒维护”等接入。日历订阅统一从“日程 → 订阅日历”进入。
7. 在专用测试环境验证收案、冲突检索、审批、案件材料、开票或用章、归档及导出；分别用经办人、审批人和无权限人员检查可见范围。

## 从 v1.2 或更早版本升级

本版包含 7 份 `20260906*` 迁移，涉及团队、审批授权、证件资料、自定义岗位及系统身份拆分。不要把更新代码当作完成迁移，也不要用 `db push` 代替迁移历史。

升级前完成数据库、文件存储、加密密钥与部署配置备份，并验证备份可恢复。在隔离环境用备份副本演练目标版本迁移，再决定生产维护窗口。迁移前停止业务写入；迁移失败应保留日志处理，不能直接重跑 seed 或清库。

关键变化：

- 原 `ADMIN` 在迁移中取得 `SUPER_ADMIN` 系统资格，其业务岗位规范为 `LAWYER`。管理员以前能够处理的业务不等于升级后仍自动有权，须按真实岗位重新配置。
- 旧管理页面迁至 `/admin/*`，旧后台网址不保留兼容；原 `/settings` 只保留个人资料与登录安全。
- 旧角色审批规则不再作为授权来源。逐项配置审批权限，检查已有待办，资料不足的申请应补正后重新提交。
- 无法还原历史材料范围的归档申请不能按当前文件推定过去齐全；须补正、重提并由审批人核验。
- 已加密文件依赖原 `STORAGE_ENCRYPTION_KEY`。升级不是换密钥；不要覆盖既有密钥和 `.env`。
- 重跑 seed 不会重置已有管理员密码，也不是升级账号权限的替代办法；它可能更新内置案由、模板等基础配置，不能作为常规升级命令盲目执行。

固定版本的操作步骤见[云服务器指南](./CLOUD-SERVER-INSTALLATION-GUIDE.md#十五升级-lawlink)。迁移后无法通过只切回旧代码可靠回退，须按已验证的备份恢复方案处理。

## 从 v1.3.x 升级：迁移基线重建（必读，含手工步骤与增量脚本）

本版把迁移链重建为单一基线 `0_init`，75 个历史迁移归档至 `prisma/migrations-archive-20260921/`（保留不删）。

起因：旧链中 `2026*` 与 `v4*` 两套命名混排，Prisma 按名称排序执行，导致补强迁移排在建列迁移之前，**整条链在空库上无法从零重放**。已应用完毕的既有库不受该缺陷影响，但全新安装与灾难恢复重建都会失败。

### 影响

| 场景 | 影响 |
|---|---|
| **全新安装** | `prisma migrate deploy` 正常跑通（含守卫恢复迁移） |
| **既有 v1.3.x 部署升级** | **必须执行增量脚本 + 两次手工标记**，只做标记会失败（见下） |
| 业务数据 | 无表级删除；新增必填列由脚本按固定规则回填（见下） |

**为什么只做标记不够**：v1.3.x 部署的库停留在 v1.3.2 的结构，缺少 v1.4.0 全部新增的表、列与枚举。若只 `resolve --applied 0_init` 后直接 `migrate deploy`，后续迁移 `20260921000004_archive_borrow` 会在 `ALTER TYPE "ReminderDeliveryObjectType"` 处报 `42704: type does not exist`，失败写入迁移表并阻断后续全部迁移；即使跳过该迁移，应用也会因缺列无法运行。**此路径已在 v1.3.2 全链重放的副本库上实测复现，不是推测。**

### 升级步骤（既有 v1.3.x 部署）

先备份数据库、`storage/` 与 `.env`，并在备份副本上演练一遍。然后：

```bash
# 1. 应用 v1.3.x → v1.4.0 的结构增量（全部建表/加列/枚举/索引，含数据回填）
#    用 psql 连接业务库执行；不要包在事务里（脚本含 ALTER TYPE ADD VALUE）
psql "$DATABASE_URL" -f prisma/upgrade/v1_3_x_to_v1_4_0.sql

# 2. 标记基线已应用（不执行 SQL，只写迁移记录；注意必须是完整目录名）
npx prisma migrate resolve --applied 0_init

# 3. 标记 archive_borrow 迁移已应用（其内容已包含在增量脚本中；
#    目录名必须完整，写成 20260921000004 会报 P3017 找不到迁移）
npx prisma migrate resolve --applied 20260921000004_archive_borrow

# 4. 正常部署（自动应用 20260921000005_restore_db_guards：恢复审计防删、
#    事项责任、财务余额等数据库层守卫——这些对象 Prisma 基线无法表达）
npx prisma migrate deploy

# 5. 确认无待办
npx prisma migrate status      # 期望：Database schema is up to date!
```

### 增量脚本的回填规则

v1.4.0 新增两处必填列 `moneyKind`（FeeEntry/Billing），脚本按 v1.3.2 的数据语义回填：

- `FeeEntry.type='COST'`（办案支出）→ `EXPENSE_RECOVERY`；其余（RECEIVABLE / RECEIVED / REFUND / COMMISSION）→ `LAWYER_FEE`
- `Billing`（委托收费约定）统一 → `LAWYER_FEE`

如所内实际与此不符，可在执行前修改脚本中两处 `UPDATE ... SET "moneyKind"` 的映射。升级后历史实收的 `confirmState` 为 `PENDING`（v1.4.0 实收两步确认规则对存量数据同样生效），由持有「确认实收到账」权限的人员在财务页确认。

### 实测记录（2026-09-21）

在 v1.3.2 tag 全链重放的副本库（含用户/案件/财务/审计数据）上按上述步骤执行，验证五项全部通过：`migrate diff` 对 `schema.prisma` 零漂移；业务数据逐表保留；10 触发器 + 5 函数 + 25 CHECK 约束 + 8 部分唯一索引与开发库一致；`DELETE FROM "AuditLog"` 被触发器拒绝；v1.4.0 应用（Prisma Client）在升级库上查询正常。

### 如果已经直接执行了 deploy 并失败

失败本身不会损坏数据（`0_init` 在第一条 `CREATE TYPE` 即中止）。先清除失败记录再按上文步骤重做：

```bash
# 若报 P3018 / 42710（type "UserRole" already exists）：失败的是 0_init
npx prisma migrate resolve --rolled-back 0_init
# 若报 42704（type "ReminderDeliveryObjectType" does not exist）：失败的是 20260921000004
npx prisma migrate resolve --rolled-back 20260921000004_archive_borrow
```

然后从步骤 1（增量脚本）开始重做。增量脚本未包事务，若中途中止请核对报错位置，或直接从备份副本重来。

### 容器部署

`docker compose` 场景在应用容器内执行上述命令，或在宿主机指向同一 `DATABASE_URL` 执行；增量脚本可经 `docker exec -i <db容器> psql -U <用户> -d <库> -f - < prisma/upgrade/v1_3_x_to_v1_4_0.sql` 送入。不要用 `prisma db push` 代替——它会绕过迁移历史，使后续升级失去可重放基准。

## 外部服务、文件与备份

默认文件存储在本实例私有目录；案件材料下载经服务端鉴权。证件照片加密存储，不进入整案导出。部署方应核对实际存储后端；如改用对象存储，应另行备份对应桶和配置。

配置外部 AI、元典或其他服务后，相应查询或识别可能将输入数据发送给所选服务；自部署不表示所有处理均在本机。应核对接收方、发送范围、密钥和服务费用。身份识别不等同实名认证。

默认 Docker 运行镜像不包含源码目录；首次 seed 需要按安装指南临时只读挂载同版本 `src/` 和 `tsconfig.json`。该挂载只用于初始化，不是日常运行方式。

默认 Docker 运行镜像也未包含 `scripts/backup.sh` 和 `pg_dump`。不要因为定时任务已注册就认为自动备份已成功；应按安装指南在宿主机安排数据库、文件和密钥备份，检查实际结果并演练恢复。本次没有宣称已完成云服务器整套部署验证。

## 验证与尚未覆盖的范围

v1.3.0 隔离副本已通过 56 个测试文件、449 项测试、lint、类型检查、Prisma 校验、生产构建和登录页启动检查。v1.3.1 的完整空库迁移、seed 和基础查询以[对应提交的 CI](https://github.com/lawflow-boop/LawLink/actions/workflows/ci.yml)为准；不能用其他提交的绿灯代替。

`/api/health` 只返回进程响应，不检查数据库连接、用户权限、备份或外部服务。正式验收须包含登录后的实际业务流程。自动测试和依赖审计不是安全认证。

本版不包含 2026-09-13 开始的 P0/P1 批次或 v4 界面开发；本地看到的后续功能不能作为对外已发布能力。

## v1.3.2：空白安装与依赖维护

公开版不附带本地模拟测试案件或数据库备份。初始化保留管理员、案由字典、流程/文书模板、用章配置与期限规则，不创建案件、客户、当事人、收案线索、材料、财务或开票记录。内置空白文书模板的文件虽存于材料表，但属于系统基础配置；CI 在独立空数据库中检查其他材料及上述业务记录为零；源码测试中的虚构样例不参与初始化。

已有部署升级不会删除原有数据，初始化程序也不承担清空演示数据的职责。开发环境中的测试数据继续保存在本地，不随本次发布上传。依赖修复及当日审计结果见 [安全说明](../SECURITY.md#依赖审计状态)。
