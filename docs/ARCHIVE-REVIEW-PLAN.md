# 归档材料审阅与完整性改造方案

日期：2026-09-06。状态：叶森已确认，已实施。

## 一、问题与核查边界

目标是让审批人能够核对实际送审文件、材料缺项及适用制度，并保证批准的卷宗与后续导出的卷宗一致。

本次依据当前工作区代码核查，未抽查具体案件文件内容，不能据此断言某一案件实际缺少材料。

| 已确认问题 | 当前实现依据 | 影响 |
| --- | --- | --- |
| 统一审批详情仅取封皮、目录两类附件 | `src/server/approval-permissions/inbox.ts` 的归档分支 | 无法从归档申请审阅实体材料 |
| 归档审批附件授权也只匹配封皮、目录 | `src/lib/approvals/documents.ts` | 仅补上文件链接，独立审批人仍可能无法读取 |
| 完整性取决于申请人传入的布尔勾选 | `src/server/archive/actions.ts`、`schemas.ts`、`src/lib/archive/checklists.ts` | 未上传文件也可被计为齐全；强制缺项提交无需逐项说明 |
| 清单为三套内置代码，没有制度版本、条款及适用性记录 | `src/lib/archive/checklists.ts` | 无从核对采用哪项律所制度；民事、刑事、行政等采用同一诉讼清单 |
| 审批通过前没有重新验证文件完整性 | `approveArchiveRecord` | 送审后文件发生变化也可能直接批准 |
| 目录按当前案件全部未删除文件生成，未固定当次送审清单；页码为空 | `src/server/archive/render.ts` | 草稿、旧次归档产物可能混入；不能表示已经完成编目和页码核对 |
| ZIP 取最新申请和案件当前文件，单文件失败用文本说明代替 | `src/server/archive/export.ts` | 导出内容可能与审批不同，缺失文件仍返回压缩包 |
| 导出路径及校验值写入该案件所有归档记录 | `src/app/api/archive/[matterId]/export/route.ts` | 不同申请的历史导出信息会被覆盖 |
| 已归档列表直接按旧缺项数组显示“齐”，且查询未按案件可见性过滤 | `src/app/(app)/archive/page.tsx`、`listArchivedMatters` | “齐”缺乏文件核验支持；案件摘要可见范围需同步修正 |

## 二、建议采用的业务规则

### 1. 归档准备：每个清单项对应实际材料

- 每项支持从本案已有材料中选择文件或上传补充材料，支持一项多文件。同一文件确有必要时可关联多个清单项。
- 区分“已关联文件”“缺失”“不适用”“待人工核验”。文件存在只表示可以审阅，不自动得出文件内容合格的结论。
- 必交项缺文件时阻止普通送审；特殊缺项申请须逐项写明原因和处理安排，审批人逐项同意并说明理由。不适用也须说明理由。
- 原件退还、纸质卷宗位置、装订、目录页码、费用处理等采用独立核验项，允许按制度配置；没有材料依据的事项不能因上传文件自动完成。
- 明确归档范围与实际程序终点；阶段性材料不作为全案已结案依据。

### 2. 归档制度：可查看原文，可追溯版本

- 管理员在现有设置体系维护归档清单：适用案件类别和程序、制度名称与版本、制度原文关联、条款提示、必交项及人工核验项。
- 制度文件复用现有律所资料；申请保存送审时的制度及清单版本，后续修改不改变历史申请。
- 内置清单作为准备参考。未配置并确认律所制度时，明确显示“未配置律所归档制度”，不显示“符合归档制度”，正式审批通过前须补齐制度依据。
- 不由系统臆造本所的实体制度要求；具体制度内容由管理员录入或关联现有原文。

### 3. 送审与审阅：固定材料，逐项核对

- 新申请保存当次材料目录：文件标识、名称、版本、大小、内容校验值、所属卷宗、清单关联和编目顺序；同时保存结案说明、缺项理由及制度版本。
- 提交前由服务端校验文件确属本案、未删除、可读取、内容校验值一致。封皮和目录按本次清单生成，旧次自动生成文书不自动混入。
- 审批详情展示“归档概况—制度依据—材料清单—核验事项—补正及历史”。每项展开可看到实际文件，PDF、图片等支持现有能力内的预览，其他格式提供下载审阅。
- 显示文件数、必交项完成情况、未关联文件、缺项及不适用理由。页码未核定时明确标示，不虚填页码。
- 审批人逐项记录核验结果和意见；未完成必需核验、文件失效或发生内容变化时，服务端阻止批准。普通通过、缺项例外通过在界面与审计中明确区分。
- 归档审批权限仅开放当次申请列明的材料及必要制度原文，不连带开放案件财务、其他附件或整案导出权限；保留材料原有专门访问限制并处理冲突，不通过归档绕过限制。

### 4. 补正与历史：每次申请可还原

- 待审批期间固定送审材料；修改或替换该批材料须先撤回或退回补正。案件其他工作可继续，新增文件不悄悄加入已送审申请。
- 同案同一归档范围仅允许一个待审申请，服务端处理重复点击与并发提交。普通、批量审批均使用同一校验服务。
- 补正后形成新的送审版本，保留旧次意见和材料关联；新文件不因某人处理过旧次申请而自动向其开放。
- 审批通过后原批次材料固定。后补材料单列补充批次并重新审批，不改变原批准目录。
- 老记录不能还原历史送审文件时显示“历史材料未固定，待核验”，不按当前文件推断过去齐全。旧待审申请须补充材料绑定与核验后重新送审。

### 5. 归档查看与导出：以批准的批次为准

- 从归档管理可直接查看归档清单、实际材料、制度版本、核验意见及补充批次。
- 导出精确指定已批准的归档记录，按该批次文件和顺序打包；文件缺失、读取失败或校验不一致时停止正式导出并列明异常。
- 目录、实际文件和导出清单保持一致；导出信息只写回该条记录。
- 旧档案未完成历史材料核验前，提供明确标注的当前材料查看能力，不能伪装成已经核定的原批准归档包。
- 同步统一归档列表、详情、文件读取和导出鉴权，实时检查账号有效性，保留既有全所角色与个人案件权限边界。

## 三、实现范围与存储方案

- 先在 `AGENTS.md`、`docs/PRD.md`、`docs/UNIFIED-APPROVAL-WORKSPACE.md` 落实获批规则。
- 复用 `ArchiveRecord.checklistJson` 保存带格式版本的归档清单与材料快照，使用专门类型和校验器区分历史布尔格式；复用 `SystemSetting` 保存带版本的律所归档规则；操作及逐项审核通过 `AuditLog` 留痕。
- 材料范围固定必须配套服务端修改门禁、文件校验与事务并发控制，不能只保存文件标识便称为冻结。制度历史文件也须保留可核验版本。
- 规则集中于现有 `src/lib/archive/`、`src/server/archive/`；复用审批工作台、案件归档向导和归档管理页面；新测试放现有 `src/tests/`。不另建临时目录。
- 优先不修改数据库 Schema，不执行迁移，不改写历史申请。若实施发现必须新增关系表或字段，单独展示设计及 SQL，再请求数据库变更批准。
- 保留当前工作区所有其他未提交改动，不触碰凭据、CI、生产部署或 Git 推送。

## 四、验收条件

1. 无文件但勾选“齐全”无法送审；跨案文件、已删除文件、失效文件不能充数。
2. 从已有材料关联及补传后，审批人能逐项预览或下载；仅有归档审批权的用户能看该批次文件，无法读取无关附件。
3. 必交缺项、不适用、人工核验均有理由与处理结果；未完成核验不能通过；批量入口不能绕过。
4. 替换送审文件、重复提交、并发审批、撤权及停用账号均有正确服务端处理。
5. 驳回补正保留旧记录；旧审批人不自动获得补正新文件；批准后补充材料与原批次分开。
6. ZIP 文件集合、顺序和内容校验与批准清单一致；读取失败不能成功返回正式归档包；只更新目标记录的导出信息。
7. 旧记录不虚报“齐全”或“符合制度”，归档列表不泄露无权查看的案件摘要。
8. 跑相关回归测试及项目要求的 lint、typecheck、Prisma validate、build；在浏览器走“准备—送审—逐项审阅—补正—通过—查看—导出”流程；核实 3000 端口进程属于本仓库且站点可访问。

## 五、实施结果

- 已用带版本的材料快照代替纯布尔勾选；申请人须逐项关联实际文件，审批人须核对每项材料、每份文件及人工核验事项。
- 已增加“设置—归档制度”，管理员关联现有律所制度原文后方可提交正式归档；系统不虚构本所制度内容。
- 已固定送审文件的名称、版本、大小、顺序与内容校验值，并限制待审材料及历史引用制度原文的删除。
- 已停用归档批量通过；旧记录明确标示“历史材料未固定”，不得据此显示“齐全”或导出可核验归档包。
- 已按获批记录生成归档包；文件缺失、读取失败、内容变化或制度原文变化时阻止正式导出，导出信息仅写回目标记录。
- 已完成 lint、typecheck、Prisma validate、生产构建和完整测试；47 个测试文件、398 项测试通过。本地 3000 端口属于本仓库，登录页正常。涉及真实制度配置、申请提交和审批决定的业务写入未在验收中代替用户操作。
